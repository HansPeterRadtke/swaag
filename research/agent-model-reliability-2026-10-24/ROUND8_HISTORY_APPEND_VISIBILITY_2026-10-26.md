## Final research-branch code change (minimal scoped durable boundary)

Two owned source files changed: `src/swaag/session_lock.py` adds `session_journal_lock`, using the existing cross-process `fcntl.flock` machinery and a per-session `history_journal.lock` sibling of the session's existing lock files; `src/swaag/history.py` takes that lock *before* the JSONL append writer starts its real SQLite transaction, holds it through `append_text()`, commit and local cached verified-stamp update. On a source stamp mismatch, a reader takes the **same per-session file lock before scanning or indexing the journal**, rechecks the exact current SQLite index cursor/file identity after waiting and retains the original hash-chain verification. The fast path for already verified unchanged journals remains unchanged. When a slow scan discovers unindexed events, the SQLite global write-intent lock is held only for the short **index update**, not during full JSONL parsing. Thus unrelated sessions can keep writing. Existing event schemas, canonical event bytes, tool/worker records, original permission boundaries and production configs remain unchanged.

**Important qualification:** The reader/writer barrier coordinates processes both using the updated code. Older code writing the same journal without the `history_journal.lock`, or raw external mutation, does not participate in that lock. External forged/same-size-tampered history remains an error: the fix does *not* skip incomplete lines or do generic JSON retries. If a writer dies after appending only half an event without committing SQLite, the permanent torn tail must still be reported as corruption, not silently called recovered. A source-lock design protects the **reader's validation boundary**, not an arbitrary source tamper or disk hardware failure.

## Original-source regression tests and fault-negative controls

The new `tests/test_history_partial_append_visibility.py` uses **real `HistoryStore` instances**, actual temporary SQLite transactions, a deterministic split-append under real OS append and `fsync`, the full original hash-chain verifier and the actual `OrchestratorEventCursor.caught_up()` path. It checks:

- A reader never completes its whole-history read, indexed-event presence check or streaming cursor's caught-up check while a session journal is only **partly appended**; after writer commit it observes the correct complete event.
- A **second OS process** with its own independently opened `HistoryStore` cannot expose an incomplete journal to the current process's stream reader; once the writer commits the terminal event is observed and its chain validates.
- With a valid but deliberately paused slow JSONL rescan on session A, an actual durable SQLite event append to **unrelated session B** succeeds before session A's scan resumes (0.8-second test bound), preventing global SQLite write-lock starvation.
- Original valid hash-chain append fast path still avoids full scans; same-length malicious modification still throws `HistoryCorruptionError`; an unsanctioned external permanently truncated JSON line **still** throws corruption.
