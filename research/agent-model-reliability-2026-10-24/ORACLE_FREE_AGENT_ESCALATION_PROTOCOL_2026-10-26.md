## Observable info and no post-grader oracle in deployable conditions

Only primary source terminal status `has_output` and primary source completed `num_steps`, source benchmark and exact configured model ID may be used to **decide an additional architecture workflow**. The 0/1 independently graded primary `resolved` and architecture-specific outcomes are allowed **only after the decision**, to measure real error and changed final success. `num_steps` is original reported reasoning step count, **not** comparable per-workflow tokens, total inference dollars, completed GPU occupancy or latency. No per-task actual token/latency/VRAM data are in this archive. A fallback means an additional complete multi-agent workflow; it cannot be priced as one paid LLM call and blindly reexecuting side-effecting workflows is disallowed in production. In this **offline counterfactual only**, triggered fallback *replaces* original terminal task result, whether correct or incorrect. This intentionally detects right-to-wrong damage without an oracle that can secretly choose a favorable result.

## Predeclared policies and costs

Evaluate **each** of the original four fixed candidate architectures without choosing a hindsight winner. For every domain and exact model/task unit, compare these source-available triggers:

1. `never`: direct single-agent outcome; zero fallback workflows.
2. `no_output`: fallback only if source `has_output=False` (deterministic failure signal for that original outcome, but poor recall of all failures).
3. `no_output_or_at_most_2_steps`: fallback if no output or original `num_steps<=2`.
4. `no_output_or_at_least_8_steps`: fallback if no output or original `num_steps>=8`.
5. `hash_budget_20pct`: exactly **28 of 140** model/task units per benchmark based on lexical SHA-256 `(seed=20261026,domain,model,task_id)` sorted ascending. Random-like, **not** a counterfactual source verifier.
6. `no_output_then_hash_budget_20pct`: exactly **28 of 140** total; prioritize no-output instances, fill remaining with same fixed SHA-256 ordering; fail instead of silently overfilling if no-output candidates exceed the fixed budget.
7. `cross_benchmark_failure_risk_budget_20pct`: fit a fixed scikit-learn `LogisticRegression(C=1.0,class_weight='balanced',solver='liblinear',max_iter=1000,random_state=20261026)` on the **other original benchmark only** with original independently graded `single-agent` failures as labels; features exactly `[no_output indicator, log1p(num_steps)]`, no current target `resolved` and no architectures' outcomes; rank heldout target model/task by predicted failure and trigger the **top 28**, ties broken SHA-256 ordering. Fit SWE-bench then evaluate Terminal-Bench, and independently fit Terminal-Bench then evaluate SWE-bench. Training benchmark labels are author-released real source results, but study source is previously inspected, so this is *retrospective cross-domain transfer*, not untouched prospective external validation. No hyperparameter tuning or role-specific posthoc threshold selection.
8. `all`: fallback on all 140 units. Extra workflow cost 140, positive and negative effects measured.
9. `verified_failure_oracle`: trigger only on `single-agent.resolved=0`, retrospective **upper bound not deployable**, included for diagnosis but never presented as a real-time available verifier.

No policy is allowed to inspect alternative-task success or target primary `resolved` when deciding except the expressly named oracle. All source-eligible alternatives are retained, including losses. No positive-only selection, no favorable per-task architecture switch, and no claim that fixed-trigger bounds prove GPU-economic superiority.

## Measures and decision threshold

For every policy/architecture/domain, count baseline correct/incorrect, fallback workflows (fully new architectures), trigger **true positives** (primary failures), trigger **false positives** (primary successes), false negative/true negative, original wrong-to-right rescued by alternative, original right-to-wrong worsened, wrong-to-wrong no improvement, right-to-right redundant completion, and **actual final externally graded successes after blindly selecting the alternative on triggered units**. Always separately report (a) gains, (b) harms, (c) *net* gain and (d) incremental workflows per net gain, if net gain positive. Also count original source `num_steps` in selected alternative workflows for **descriptive workload characteristics only**, never claim true tokens or latency. For `no_output` check whether it can ever harm a primary correct outcome (source says no-output implies unresolved). For `all`, final outcome must equal original architecture's external grade. Include negative controls of source-forced hash selection and never, plus nondeployable verified-failure oracle.

Predeclare **task-ID clustered bootstrap** with seed 20261026 and 1,000 resamples over **20 source task IDs** per benchmark, carrying all seven repeated model-version outcomes for each sampled task; compare each candidate against never and the `hash_budget_20pct` control at same number of attempts where applicable. These are **descriptive** intervals because outcomes across model IDs and task IDs are correlated and sample is tiny. Do not count 140 repeated model/task rows as 140 independent tasks. Keep predictions/outcomes in a lossless derived source-keyed CSV/JSON (no full copyrighted source text); hash all originals. Do not treat no-output, model votes, low task steps or source classifier probability as proof of semantic error beyond the exact property they establish.
