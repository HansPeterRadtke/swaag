## New candidate availability verification, and important earlier ScreenVLM correction

The official [ScreenVLM](https://huggingface.co/docling-project/ScreenVLM) model card specifies **up to 6,192 generated tokens** in its complete screen parsing example. The earlier Nitro CPU test allowed **384** generated tokens, used small target-only crops, and cut off two of its four outputs. Its recorded **zero of four intended text strings** is a valid result of that constrained *configuration*, **not an unbiased evaluation of full-page ScreenVLM v2**. The earlier raw output remains unmodified and the prior research failure is not hidden; the overall model capability remains unknown. Its Idefics3/Granite 316M full-page ScreenTag generation can be impractically slow on busy CPUs, so more capable GPU evaluation must wait for demonstrably idle and appropriately sized hardware. The model is an element parser; text/box output alone does not prove GUI correctness.

A more purpose-appropriate installable complement is [ScreenParser](https://huggingface.co/docling-project/ScreenParser), IBM/ETH's ScreenParse-v2-trained YOLO11-Large **55-class UI element detector**. Pinned source revision: `f029e565f1206577402e43206454522075be3f72`; real published weight file `best.pt`, **153,259,543 bytes**, SHA256 `dbcb4f583ccfdb8100a68e606525c247890a2de4c1a54b14741e0ee29ce0ab88`. The original weights are kept under isolated `/data/var/perceptual-independent-20261024/models/ScreenParser-YOLO`, **not Git**. PyTorch 2.5.1 and Ultralytics 8.3.221 were made available in an isolated Python interpreter, using only preinstalled read-only PyTorch/OpenCV dependencies; no shared Python environment changed. The official model settings `imgsz=1280, conf=0.10, iou=0.10`, one low-priority CPU thread, 32 original real-site UIJudgeBench target-centered **whole viewport screenshots**, author-verified target boxes and clean/defective labels kept separate from detector inputs. The original 32 Firefox full-viewport images were newly captured read-only from archived real sites; all elements intersect the target screenshot, though two source variants may still share identical pixels. The raw bounding-box predictions and task-level target-IoU scoring are distinctly separated in `tests/research/screenparser_yolo_real_ui_eval.py`. **Observed initial feasibility only:** the checkpoint loaded, exposed 55 classes, and returned 39 boxes on the first full website screenshot, but CPU inference took **138.856 seconds for that single screen** under Nitro's high shared load. This is not deployment-grade real-time CPU behavior, nor full benchmark accuracy. Later model results had **not been verified as complete at this report checkpoint**. Do not elevate availability/one inference to an accepted GUI judge.

**Licensing matters for eventual commercial tooling:** the `docling-project/ScreenParser` model card identifies weights as **Apache 2.0**, but the tested **Ultralytics runtime** is distributed under AGPL-3.0/Enterprise licensing as described by [Ultralytics' official license](https://www.ultralytics.com/license). Alternative detector/runtime/export stacks must be reviewed for their own licensing. Microsoft's [OmniParser v2](https://huggingface.co/microsoft/OmniParser-v2.0) has a separate MIT-licensed YOLOv9-E icon-detection route plus MIT icon-captioner, unlike the older AGPL YOLOv8 icon detector; no corresponding local prediction accuracy has yet been measured.

## Narrow engineering decisions and remaining work

For web products with actual DOM, prefer **instrumented accessibility and layout tools** (`axe-core` plus target/client/scroll/ancestor bounds) where the underlying property is precisely measurable, accompanied by screenshots and explicit unknowns. OCR/ScreenParser can provide evidence about what *appears* to exist, not whether the screen is correct; user-specific intention such as allowed ellipsis/overlap and the intended text remain necessary. For diagrams, trust the authoritative graph/chart/TikZ data and independently compare visual labels/positions; no tested general VLM has an accepted independent diagram-semantics score. For owned Blender/CAD mechanical objects, trust exact scene units, identities, joints, supported contacts, real physics, depth and multiview geometry for narrow assertions, then independently human-calibrated learned models for appearance—none yet qualified for real industrial photorealism or missing mechanical parts. For moving video, use exact PTS/frame-timeline/approved cut and hold contracts for deterministic faults; a human-validated video model or physics-invariant tracker is **still unverified** for unattended acceptance. Mere agreement across multiple VLMs, previously shown to miss most of thirty-one expert-labeled missing-parts defects, is not a solution.

**Still genuinely open:** a reproducible specialist visual parser benchmark on complete real software interfaces with separately certified visible clipping, overlaps and low contrast; independent rendered *mechanical* CAD/physical impossibility examples including real-world reference dimensions, supports, joints and material/light plausibility; and a timestamped true-good-versus-true-bad *natural* video stutter/judder/error set with controlled codec and source FPS, plus a modern real video-language judge calibrated on untouched source prompt groups. Tests already selected/tuned on publicly known samples are research diagnostics and need further untouched datasets before deployment.

## Verified post-checkpoint addendum — real full-page ScreenParser outcome (2026-10-25)

**The previously pending 32-image ScreenParser CPU run subsequently completed**, and its original frozen model predictions, 32 Firefox capture/source receipts, independent DOM target boxes and source-paired comparisons were verified **without re-running inference**. The immutable raw/source files remain under `/data/var/perceptual-independent-20261024/screenparser-fullpage-real/`; the code-only reproduction/score scripts are `screenparser_fullpage_corpus.py`, `screenparser_yolo_real_ui_eval.py`, `screenparser_paired_source_audit_20261025.py`, and `publish_screenparser_verified_20261025.py` in SWAAG `tests/research`. Compact source-linked verified facts are in `perceptual-screenparser-verified-evidence-2026-10-25.json`.

On 32 genuine Firefox whole-viewport captures (16 externally DOM-labeled faulty sites plus 16 clean controls, representing 16 paired UI questions over 15 source website families), ScreenParser returned **55 class types** and an average of 45.5 boxes per screenshot. A matching predicted *non-generic element* had intersection-over-union at least **0.50** with the ONE externally identified target browser DOM rectangle in only **11 of 32** cases: **3 of 16 faulty source targets** and **8 of 16 clean controls**. At IoU 0.30 the outcomes were 5 faulty versus 9 controls; at IoU 0.10, 7 faulty versus 15 controls. Total run **2039.73 seconds** on loaded Nitro CPU, per-image mean **63.418 seconds**, median **57.18 seconds**, 10th–90th percentile around **49.97–82.68 seconds**, peak measured process resident memory **1,032,608 KB**. No Nitro GPU, Thor or user model was used. The actual Firefox viewport images were **1920 × 994 pixels** after the browser's headless window capture, not the nominal 1920×1080 window setting.

The paired comparison held the target site and question fixed within each of 16 pairs. On **15 of 16 pairs**, model-to-source bounding-box IoU was higher for the clean version; mean clean IoU **0.48995** versus defective **0.19923**, paired difference **0.29072** (website-family bootstrap 95% descriptive range **0.165–0.424**, not a deployment accuracy interval). One clean/defective site pair had **byte-identical screenshot pixels despite different source-labelled DOM defect status**. This makes any screenshot-only classifier incapable of distinguishing its DOM label in that example, independently of model quality. ScreenParser is an *element locator*, not a defect classifier; its lower defective-box IoU partly reflects a **fundamental oracle mismatch** when a true clipped/overflowing source CSS element extends beyond the actual visible-pixel region, and YOLO recognizes visible child regions. It would be a serious interpretive error to treat 3/16 or 11/32 as ScreenParser's general UI parsing mAP, text readability recall, or clipping classifier accuracy. The source benchmark supplies only ONE selected target element per page, not exhaustive human element-box truth. Further research would require independent exhaustive visible box annotations, exact text visibility and intended layout semantics, and task-specific ROI policy.

**Operational conclusion:** the actual pinned 153.26MB YOLO11-L checkpoint can find many plausible controls/links/text regions on natural website screenshots, but at one minute per full-page CPU image on heavily loaded Nitro and with poor agreement to some source-target boxes, it is unsuitable *in the measured configuration* as a real-time or standalone acceptance judge. UI-specific parsers may still assist OCR/screenshot localization; DOM-backed `axe-core`, real browser scroll/client/ancestor geometries and expected visible text remain the evidence-backed deterministic checks for the narrow applicable properties. The prior four cropped ScreenVLM tests were constrained to 384 output tokens versus its official 6192-token example, so their zero recovered intended labels do **not** establish full-page failure of that distinct model.

Neither was retried or indirectly reconstructed, and neither is counted as completed analysis. The independently verified warehouse/dock presentation timestamp and downscaled motion results in `perceptual-owner-video-verified-signal-2026-10-25.json` remain separate, with no verified full-resolution duplicate or subjective stutter verdict.
