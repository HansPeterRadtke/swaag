# Full Infra guideline topic coverage for SWAAG — 2026-10-21

This corrects a substantive scope error in earlier SWAAG compliance summaries: those reports focused mainly on the core conversation/worker/voice system, despite the user explicitly requesting **the whole Infra guideline corpus**. Mechanical file inventory is not proposition-by-proposition semantic reading or proof that every guideline is implemented. This index includes every normalized Markdown guideline/supporting document present in Infra at the time of generation. Source recordings remain the governing evidence. Nothing here modifies original recordings or other project repositories.

Two obligations differ: **SWAAG-core requirements** concern the assistant's own operation, safety, communication, tools, context and UI; **task-domain requirements** must be discovered, loaded and obeyed when SWAAG works on an actual trading, game, robotics, knowledge, GUI, mail/calendar or other domain project. Domain rules are not satisfied merely because the agent can read them, nor are they always features that belong inside SWAAG's runtime. A tested agent kernel does not prove the correctness of a game engine, a live broker strategy or a robot controller.

## Previously omitted or insufficiently distinguished substantive families

The prior report did not separately close these requirements:

- **Agent operation and user authority:** exact user wording, direct questions versus orders versus hypotheticals, durable editable user policy, model-specific minimal prompts, source-preserving compaction, semantic context selection and grounding, independently checked task/subtask completion, fail-safe background continuation, one orchestrator managing prioritized dependent/parallel workers, interruptions, questions and criticality, reversible scheduling and waiting, and agent-owned reusable tool workspaces with actual host quotas. Existing SWAAG tests exercise important mechanisms, not every natural-language decision.
- **Software engineering and algorithm selection:** architecture traced from required inputs through observable effects, explicit pre/postconditions and error branches, platform-specific feasibility probes, meaningful modularity/naming, testable state-machine and concurrency contracts, correct algorithm family for the mathematical problem, constrained grid/random/evolutionary/gradient search spaces and objective functions, reuse of safe one-time setup rather than repeated initialization, and independent cost/speed/resource measurements. Not all two thousand-plus source routines have independently established complete boundary/path coverage.
- **Testing and evidence:** valid/invalid parameter combinations, all meaningful control paths, injected faults/timeouts/disconnects, end-to-end hardware/user journeys, test-oracle independence, property/fuzz checks and reproducible failure seeds, model/prompt holdouts that remain unseen during tuning, nested holdouts after selection, source-vintage/chronological anti-leakage, perceptual audio/image/video evaluation with actually qualified analyzers, and no substitution of schema validity for semantic correctness.
- **Configuration, logging, security and performance:** audit every runtime-changing literal, semantic setting metadata/unit/range/dependencies, deterministic override provenance, bounded queues/caches/retries, diagnostic levels and crash-persistent event traces, private-data and secret redaction, retention/rotation limits, process/subprocess/mount and model/server quotas, genuine transport trust boundaries, and measured end-to-end latency. Host-wide hardening, disk reclamation and cross-host quotas are not certified by SWAAG unit tests.
- **Entire GUI/HMI suite:** screen question/purpose contracts, visible system health, relative priority and truthful warning semantics, immediate local acceptance within a frame, meaningful in-progress/failed/rejected/empty/stale states, progressive disclosure instead of dumping dataframes, suitable visual charts/metrics/tables, nonoverlapping responsive layouts, legible scalable text/touch regions, phone/tablet/desktop/web/Qt platform-specific acceptance, controls for disabling automation, screenshot or rendered-output inspection, and approved contextual voice/screen feedback with exact build and event provenance. GUI **financial domain screens** carry additional explicit questions for trading, options, optimization, backtesting and portfolio views.
- **Voice HMI:** controllable automatic STT/send and full manual editable input, retained original audio and corrected vocabulary, true semantic turn finality, safe interruption versus noise/backchannel, device microphone/service/model readiness, play/pause/seek/replay and stable duration/current/remaining times in every audio player, dedicated full outstanding-worker-question interface, audio style, foreground TTS/background overlap and physical Android playback tests. Emulator transport/AudioTrack evidence is not full physical-phone acceptance.
- **Networking and transport:** classify streams as reliable commands, durable complete media, best-effort live media, replaceable state or bulk; choose TCP/WebSocket/QUIC/UDP only after topology/latency/goodput measurement; continuity/quality buffering; stable source IDs and exact receiver acknowledgements for non-idempotent effects; jitter/backoff/gap/duplication/disconnect simulation; do not invent custom retransmission as an alleged universal optimization.
- **Know More Dirt (KMD):** original file/metadata identity, exact source-linked chunks with offsets, model/version-aware sentence/passage embeddings, semantic vector discovery, context spanning chunks/files, DRT/DRS referent/scope/negation/tense/quoted/dream/fiction/conditional protection, and updatable/revocable source-grounded memory. SWAAG long-context retrieval is a related component, not an audited replacement for this separate system.
- **Trading:** raw/provider provenance and conflicting data reconciliation, identity/venue/corporate-action/vintage mapping and point-in-time available-at, fees/slippage/liquidity/buyers/fills, realistic cash-secured-put collateral/assignment/share-liquidation semantics, chronological historical/out-of-sample tests and unoptimized final holdouts, causal mechanism research, DCF variants and valuation-crossing controls, publicly verifiable network hypotheses without converting allegations into facts, quantified stability/drawdowns and explicit scenario assumptions. The Trading project's own experiment results must be examined before claiming success.
- **Games:** engine-independent *authoritative 3D* simulation with text/2D/3D adapters, physical/semantic world materialization and persistence (PRSE), text↔physics event round trips, meaningful visible scene interactions, controls from low-level inputs to interruptible semantic goals, playability/onboarding/humor/standard input conventions, save-anywhere and faithful reload, human/creature physical capability/skill/health states, hidden cyclical systems discovered experimentally, and manually demonstrated compact learned habits with real rollout testing and optional player activation.
- **Robotics:** explicit state/action/sensor/actuator definitions and units, synchronized demonstration timestamps and normalization/leakage controls, planning versus value iteration/Q-learning versus feedback, model-free RL versus behavior cloning and multitask/end-to-end learners, shared preprocessing and reusable bounded low-level skills, physical safety/error limits, small simulations and published algorithm comparison before actual robot deployment.
- **Recording-to-guideline conversion and original research:** preserve original text and provenance without weakening or inventing rules, distinguish binding instructions from brainstorming and research questions, research implementation choices instead of repeatedly asking the owner, retain falsified alternatives and semantic qualifiers, and continuously reconcile new recordings against canonical sources. Preserving files/checksums is not itself proof of complete semantic proposition coverage.
- **Additional Infra-owned integrations outside this normalized topic tree:** Google account/mail/Calendar/YouTube/Drive service ownership and OAuth boundaries, dedicated versus personal accounts, source/installed configuration and live effects, scheduler reliability and Android calendar behavior. These runbooks are under Infra's separate Google operations documentation; they are not silently included in SWAAG-core compliance.

## Status classification and honest release boundary

The existing SWAAG core has passing mechanistic tests for durable conversation receipts, user corrections, indexed replay, worker scheduling and state snapshots, structured model responses and fallback, and some emulator audio stages. Those findings **must not** be extrapolated to arbitrary correct semantic judgments, every possible failure path, or all the distinct product-specific repositories. None of the individual domain families listed below can be labeled fully implemented-and-tested from the SWAAG regression suite alone. Research topics in a guideline are obligations to investigate when relevant, **not** indications that a generic code module is missing from SWAAG. A record with no pending worker questions does not indicate that the Infra research backlog is empty.

Critical unclosed gates still include difficult distant semantic/discourse relevance and goal supersession, complete human-in-the-loop/real-phone UX, GPU/worker preemption under contention, host quotas and low-disk protection, actual tool/workspace sandbox enforcement and authoritative verification of domain work. The old October ninth audit also lists concrete experiments in KMD discourse, market vintage/DCF, game-core physics and learned skills, networking conditions and robotics algorithms. Each item requires an independently dated result or explicit unverified status; do not represent these as awaiting user clarification.
