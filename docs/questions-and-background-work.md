# Durable questions and authorized background work

Unresolved questions are a projection of canonical session history. The question ID is the original `agent_question` event ID; criticality, reason, provisional assumption, and source sequence are retained exactly. User messages do not silently resolve questions. Legacy checkpoints without question state are rebuilt from history on first load.

The `questions` capability lists unresolved questions or records an explicit resolution: `answered_by_user`, `answered_by_research`, `superseded`, `irrelevant`, or `expired`. Every resolution cites existing history event sequences and includes a reason. User answers require a user-message source; research answers require recorded tool/source evidence. These are provenance checks: the model still decides whether the evidence actually answers the question. Assumptions remain provisional. Resolved questions leave active state, while their original event and complete resolution remain in exact history. Worker/AG-UI streams expose question and resolution events, including a stable question ID.

Unresolved state is included in normal action context. Full content is used when it fits; measured overflow can use the existing semantic projection/recovery path. The `questions.list` locator recovers exact current state. When that capability is disabled, the source cannot be projected through an unavailable recovery tool. `runtime.max_open_questions` defaults to 128 entries; `runtime.max_open_question_chars` defaults to 65,536 combined question/reason/assumption characters. Both are positive configurable limits. Capacity pressure rejects new questions without deleting existing questions or preventing useful actions and resolution calls.

Background work uses existing orchestration plans and workers. It does not invent tasks or authorization. Create a complete unstarted plan, then use `background_work.enqueue` with the plan ID and the exact history sequence of the authorizing user message. The tool binds the source to its current session. The transport API is `orchestration.backlog.enqueue`, with `plan_id`, `authorization_session_id`, and `authorization_event_sequence`; inspection/cancellation use `orchestration.backlog.list` and `orchestration.backlog.cancel`. The control endpoint retains the service's existing local trust boundary.

The enqueue transaction stores the authorization event hash and reviewed plan revision. Missing sources, non-user sources, invalid/empty plans, bound workers, and queue overflow fail closed. Interpreting the user's scope remains a model responsibility: citing any user message does not make unrelated work authorized. A later plan revision holds the entry until the current plan is reviewed and explicitly queued again. Exact enqueue retries are idempotent.

`communication.idle_work_mode` defaults to `finish_only`: queued work persists but is never automatically started. `authorized_backlog` is an explicit deployment opt-in to dispatch authorized plans after foreground work finishes. The dispatcher defers while any plan is active, any worker is queued/working/canceling/waiting for input, a communication request is queued/processing, or a direct runtime turn has an active marker. It claims only one plan atomically. A crash after the claim is recovered by normal active-plan advancement. It uses the existing worker/model scheduling and resource policy. It does not preempt a running background task when a new foreground task arrives; subsequent model calls use the existing shared scheduler and user-control mechanisms.

`communication.max_background_plans` defaults to 128 pending/held plans. It is a positive count. Overflow rejects additions without discarding work. `background_work.cancel` removes queued work; cancel an already running plan through the existing orchestration cancellation operation. A queued/held plan cannot bypass idle policy through ordinary start polling; cancel its backlog entry before explicitly starting it immediately. The service remains in `finish_only` unless the user changes that setting. Optional autonomous idea generation has not been enabled.

Tests cover exact replay, legacy checkpoint migration, all resolution types, invalid evidence, capacity pressure, default-disabled behavior, foreground deferral, authorization provenance, changed-plan holds, idempotency, cancellation, concurrent dispatch, and recovery after a dispatch commit. These mechanical tests do not certify that every model will interpret authorization or questions correctly; live semantic acceptance is a separate gate.

## Queue and cache pressure

Execution concurrency and pending capacity are separate. `communication.max_active_workers` defaults to 128 queued/working/canceling workers across managers sharing the worker store; `communication.max_pending_requests` defaults to 128 queued/processing control-service requests. `runtime.max_pending_controls` defaults to 256 unprocessed controls per session, and `runtime.max_pending_inference` defaults to 256 queued/running/suspended calls per backend. These are positive integer counts. SQLite admission counts and writes share a write transaction, so concurrent callers cannot exceed a bound by racing. Rejection preserves accepted work and leaves rejected worker starts unmodified. Same-session control-ID retries retain the originally accepted payload; cross-session ID reuse is rejected. Completed worker futures are released; a deferred callback cannot duplicate a replacement future.

`context.max_token_count_cache_entries` defaults to 4,096 memo entries. FIFO eviction causes recomputation, not loss of canonical tokenization evidence. `model.cache_max_bytes` defaults to 134,217,728 bytes and `model.cache_max_entries` to 16,384 combined completion/rendering/token-count entries. Cassette reads are bounded before JSON decoding. Recording beyond either cap fails explicitly and leaves the previously committed cassette unchanged, including exact replay evidence. Archive the old cassette or configure a new path before further recording; increasing a limit consumes more memory/storage. `model.cache_lock_stripes` defaults to 128 request-lock files per cassette, and in-process locks have weak ownership. Change stripe count only while all cassette users are stopped, because processes must agree on lock mapping. Existing old lock files are not deleted by deployment.

These limits bound active queues and caches, not authoritative historical evidence. Session/worker/plan histories remain durable and follow the existing archive policy. Optional embedding-index and external callback retention still require their own lifetime-pressure acceptance.

All ten SQLite store factories now close each owned connection on context exit, including setup and operation failures. Transaction commit/rollback behavior is preserved. Connections no longer depend on cyclic garbage collection to release database and journal file handles; this was a real full-suite failure at the normal descriptor limit, not merely an optional optimization.
