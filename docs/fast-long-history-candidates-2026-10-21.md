# Fast first-response long-range history candidates — October 21, 2026

## Problem and measured cause

The first SWAAG Coder step previously saw up to six recent whole conversation messages plus current worker state, durable scoped user policy and notes, but omitted all other older conversational source unless the main orchestrator retrieved it after first speech. Correctly interpreting a question about a historic project or old explicitly named constraint could therefore require an extra full orchestration pass even when an exact source answer was already indexed. General `HistoryStore.query_history_details()` uses a global FTS5 index containing tool output and model telemetry; production read-only measurements for a common term returned in roughly **700–1,200 milliseconds** on Thor's 1.3-gigabyte history SQLite database.

The existing `(session_id, event_type, sequence)` index permits scanning only the current session's `message_added` user utterances. Real read-only comparisons took **about two to nine milliseconds** for the same topics. This is a derived navigation aid, not an independent semantic oracle.

## Implemented

`fast_history_candidates.py` provides optional, indexed, scoped, bounded lexical-overlap candidates from *all older* exact user messages, not from an arbitrary last-N history window. Only the precise `message_added` user content is read; assistant claims, model output and tool receipts are excluded from these extra candidates. The returned entries retain exact event sequence, event hash, timestamp, match score and the **whole unaltered content only if it fits** the dedicated character budget. Larger records are represented by exact event pointers, never partly quoted or blindly shortened where the omitted half might contain a critical prohibition. The original canonical source and all non-returned passages remain untouched and retrievable through `history_window`/`history_search`.

The candidate source explicitly says that lexical overlap is **not semantic relevance**, that an older user utterance is historical evidence rather than a new active instruction, and that a later change of mind may have superseded it. The current complete user message, durable active policies and fresh worker facts continue to govern the turn. No tool permission or worker action is inferred from a candidate. If no discriminating query terms exist, no indexed record matches, the index is behind the durable session cursor, a SQLite read fails or the tiny optional wall-time budget expires, the fast model still receives the current message and known facts; it must delegate for missing historical facts rather than invent them.

Three validated configuration parameters separate the candidate count, aggregate exact character budget and maximum indexed lookup time. By default they allow at most four message candidates, about fourteen hundred verbatim characters, and seventy-five milliseconds of optional local SQLite work. On context pressure the candidates are removed by a second **deterministic budget compilation** before falling back to the full orchestrator; no second model inference is introduced solely because a candidate was too long.

## Tests and real model acceptance

The deterministic tests verify an exact old constraint beyond one hundred and sixty newer messages, correct session scoping and event provenance, exclusion of unrelated older finance text, an oversized user record represented only by its exact reference, missing index and broken SQLite fallback, SQL parameter safety, non-English tokens, quoted/hypothetical instructions as data, original current-message precedence and one model request with or without optional candidates. They specifically forbid loading the entire durable event journal for old user-message lookup.

An isolated real Thor Qwen3-Coder generation was then run against a synthetic old warehouse constraint separated from the current question by fourteen independent later user messages. The first model call had **1,668 input tokens**, took **8.18 seconds** end-to-end, selected **answer** rather than dispatching a worker, and correctly repeated both conditions: GPU-only rendering and preservation of the original PBR material textures. It did not alter the actual live user session, workers or model configurations. This single success does **not** establish universally correct semantic relevance; adversarial long-distance history and supersession remain ongoing quality gates.

## Limits

This is low-cost **candidate discovery**, not a complete relevance selector. There is no pretense that a lexical search reliably connects every paraphrase, pronoun or indirect reference. Ambiguous deictic messages such as "go on" still require the full controller and source history. A limited, user-relevant candidate is not evidence that all prior constraints have been found; important full-source task decisions remain the main controller's responsibility. The extra first-stage search is bounded and fallible and cannot guarantee the user's desired perfect history selection. It improves the evidence available for straightforward historically anchored questions without slowing unrelated greetings or losing evidence.
