# Transport-neutral task API

> Developer/integration API, not the ordinary user conversation port.
>
> The canonical human/user entry point is orchestrator.message. Voice and chat frontends send ordinary finalized user messages there. Task API and the protocol adapters documented below are for explicit task/worker lifecycle integration, automation, interoperability, debugging, and advanced clients that intentionally address task state. They MUST NOT be treated as equivalent user-facing entrances or used by a normal voice frontend to decide when to create a worker.


`TaskApi` is the internal command/query boundary used by the communication service and protocol adapters. Worker state and events remain authoritative; transports do not own task lifecycle semantics.

`OrchestrationApi` is the parallel transport-neutral control boundary for the user-facing orchestrator. It owns no semantic policy by itself: the orchestrator model authors durable plans and semantic branch decisions, while deterministic code validates graph structure, resource/model availability, lifecycle invariants, scheduling admission, persistence, and delivery cursors. A plan stores the overall user objective, scheduling/reporting policy, resource limits, durable worker nodes, finish/abort criteria, model route, weight, node resource request, and dependency edges with explicit conditions and output-to-input mappings. Plan revisions and dependency resolutions are append-only events. Starting a draft first performs mechanical validation and fails closed before launching any worker if the plan is empty, references an unavailable model route, binds a missing/mismatched worker, or contains an impossible declared resource request. Cycles are rejected when edges are added.

Scheduling supports sequential/exclusive release and bounded parallel release. Independent runnable nodes are ordered by plan priority. Each durable worker carries that priority as its inference weight; the backend-neutral inference coordinator applies weighted-fair virtual service within the highest effective priority class, while queue aging prevents starvation. User-facing orchestrator calls run at control priority and, when sharing a backend, preempt the exact owning worker runtime and replay its request from durable context afterward. Named model routes are configured through `communication.model_routes`; changing a bound worker to another route requires explicit worker replacement instead of silently migrating live inference.

Plan resource limits are mechanical named numeric budgets. Nodes may declare named requests such as RAM or API slots; the scheduler accounts active allocations before release and fails closed if one request exceeds the plan limit. The `system_resources` tool supplies current host memory, swap, CPU/load, and filesystem capacity as mechanical facts; the LLM remains responsible for deciding what limits and assignments make semantic sense.

Reporting modes are `all`, `terminal`, `important`, `completion_only`, and `manual`. Worker/plan facts first become durable orchestration events. Selected user notifications enter a sequence-numbered durable outbox; critical failures bypass suppression. `notifications`, `notifications.wait`, and `notification.ack` provide resumable cursor access and acknowledgement. The loopback listener also exposes `GET /orchestration/{plan_id}/notifications` as `text/event-stream`, with `after_sequence` and `unacknowledged_only` query controls, keepalives, and terminal closure, so clients can receive push-style plan updates without owning lifecycle state.

## Caller-defined structured output

The `create` operation may include `output_schema` and `mechanical_fields`:

```json
{
  "objective": "Audit the release and report the finding.",
  "output_schema": {
    "type": "object",
    "properties": {
      "finding": {"type": "string"},
      "confidence": {"type": "string", "enum": ["low", "high"]},
      "worker": {"type": "string"},
      "state": {"type": "string", "enum": ["completed"]}
    },
    "required": ["finding", "confidence", "worker", "state"],
    "additionalProperties": false
  },
  "mechanical_fields": {
    "worker": "worker_id",
    "state": "status"
  },
  "start": true
}
```

Schemas must satisfy Swaag's portable closed-schema subset. Mechanical bindings address top-level output fields and may use `worker_id`, `session_id`, `objective`, `status`, `created_at`, `started_at`, or `run_count`. Those fields never enter the semantic generation schema. Remaining fields are generated by an LLM call that uses the central context compiler, actual schema-constrained decoding, full-fidelity evidence when it fits, and measured semantic tool-result reduction only on overflow.

The final merged object is mechanically validated against the caller's complete schema and stored in the terminal worker event. `get` returns it as `structured_output`. The ordinary textual worker `result` is always retained as the transport-independent common-denominator response.

## Optional response presentations

Task creation may include `"presentation_modes": ["visual", "audio"]`. These are optional durable derivative variants of a transport-neutral worker result; an omitted or empty array adds no presentation model calls and leaves that verified raw result unchanged. They are distinct from the ordinary chat policy: user-facing natural-language assistant/status/orchestrator messages use audio style by default unless the user explicitly requests an exact, visual, code, or machine-readable representation. `visual` runs a separately context-compiled semantic relevance editor over the exact worker result. The explicit `audio` presentation variant first uses that selected information, then runs a separate transformation suitable for clients that want a retained audio-rendered artifact. An independent constrained model call compares each optional candidate with the exact source and user request; rejected candidates receive bounded evidence-based repair, and an unverified candidate is never reported as completed.

The raw worker result remains `result`. Successful or unavailable variants, exact source/output hashes, evaluations, attempts, and failures are durable history/worker events, while `get` and task-create/start responses expose the terminal `presentations` object. Continuous workers reject terminal presentation modes because they intentionally have no final response boundary. The default remains disabled until live one-call/staged and small-model experiments justify a deployment policy.

Run the checkpointed live comparison with `python -m swaag.benchmark response-presentation --output /data/var/swaag/benchmarks/response-presentation`. Repeat with `--model-base-url` for an alternate small-model or device endpoint; results retain each model-call kind, context compilation, independent evaluation, latency, and exact rendered answer.

Status questions use a separate context-compiled operation over exact worker events and mechanical state. When `communication.model_base_url` selects a separate runtime, its constrained status output can request stronger interpretation. Swaag then sends the unchanged evidence snapshot to the main runtime at communication priority and records integrity-linked escalation request, resolution or failure events. Run `python -m swaag.benchmark communication-routing --assistant-model-base-url URL --output /data/var/swaag/benchmarks/communication-routing` before relying on a smaller model in production.

For concurrent voice or chat operation, ordinary finalized user utterances go to the persistent user-facing orchestrator through orchestrator.message. Its first constrained semantic call either answers lightweight conversation immediately with no worker, or routes substantive work into the full orchestration planner. Direct Task API worker messages and controls remain lower-level explicitly worker-addressed operations, not the default human conversation path. Genuine simultaneous inference still requires separate backend capacity or shared-backend preemption and replay. For Android, STT, TTS, and presentation routing, see voice-and-communication.md.

## Durable event cursors

`events` returns worker events after `after_sequence` with a bounded `limit`. `events.wait` uses the same cursor and waits up to 60 seconds for a new event or an input-required/terminal state; its `timed_out` and `terminal` fields distinguish those outcomes. Reissuing the request with `next_sequence` is resumable and does not depend on a live connection.

Worker lifecycle rows stay small. Stream-worthy canonical session events are linked by session ID, sequence, event ID, type, and integrity hash. A read hydrates the exact append-only source event on demand and rejects a mismatched reference; raw tool results and semantic status are therefore not copied into a second authority. The AG-UI view maps linked tool calls/results, semantic status, questions, assistant progress, and shared-state updates into protocol events. `ag_ui.subscribe` remains the transport-neutral bounded cursor wait used beneath richer adapters.

The same listener now accepts a standard AG-UI `RunAgentInput` as `POST /ag-ui` and returns unwrapped AG-UI events over `text/event-stream`. The client-owned `threadId` maps durably to one worker and each `runId` maps to exact worker-event start/end cursors, allowing an idempotent retry to replay that run without starting it twice. A newer run closes the previous stream boundary; replay reports a superseded run honestly instead of assigning later events to the old run ID. The stream starts with the supplied thread/run IDs, follows canonical worker events without holding inference admission, and closes on success, failure, cancellation, or a resumable interrupt.

`GET /ag-ui/capabilities` returns the current official `AgentCapabilities` shape. It derives the backend-tool inventory and exact input schemas from the effective runtime registry, declares only implemented protocol behavior and does not advertise a fictitious production iteration bound. SSE streaming, state snapshots, state deltas, state persistence within a thread, resumable human interrupts, and sequential client-provided tools are supported. WebSocket, binary HTTP, push delivery, sequence-number stream resume, parallel calls, and AG-UI caller-defined structured output remain explicitly false. The response is dynamic and `no-store`; unsupported methods fail with `405` rather than being mistaken for a run request.

For a new thread, the complete supplied textual conversation seeds the durable objective. Later runs add the current user request. Typed inline AG-UI image/audio/video/document data and legacy binary data enter raw attachment storage; URL/reference inputs are disclosed to the worker but never fetched implicitly. Caller context is preserved. Every accepted run binds an exact append-only shared-state revision to its run ID, includes that current state with hash/revision provenance in the worker's ordinary full-fidelity context, and emits the same value as `STATE_SNAPSHOT`; retry replay cannot replace the state originally bound to a run. An omitted state inherits the last accepted thread revision.

Only a worker session currently bound to an AG-UI thread discovers the `shared_state` capability. Its read operation returns the complete current state and provenance. Its mutation operation accepts standard RFC 6902 add/remove/replace/move/copy/test operations, but requires the exact base revision and state hash observed by the worker. Swaag applies the ordered patch atomically to a copy, rejects an invalid or no-op patch, and returns the complete current revision as conflict evidence instead of blindly merging concurrent client changes. Every successful update stores the exact resulting state, patch, state/patch hashes, source session/call, base lineage, and canonical history-event link before it is projected as `STATE_DELTA`; service startup verifies every linked update and repairs the narrow cross-store crash window from the durable patch without inventing state. The full result remains ordinary recoverable tool evidence, while semantic decisions about whether and what to change remain with the LLM. The next client run may still supply a complete replacement snapshot because AG-UI state is bidirectional. Forwarded props fail explicitly because silently discarding them would be incorrect. A `resume` entry must address the exact durable open interrupt ID; resolved payloads become user input and canceled responses use normal worker cancellation.

`RunAgentInput.tools` may define client-executed capabilities using Swaag's portable closed JSON-schema subset. A run binds the exact catalog, metadata, hash, source thread, and run ID as a durable revision. Catalog names cannot shadow any server capability. Client tools enter the same compact capability index and staged schema-selection path as server tools, so semantic selection remains model-owned and exact schemas consume context only when selected. A selected client call is validated and persisted with exact arguments and lineage, then the worker enters a distinct client-execution wait and the AG-UI run ends successfully after emitting the ordinary `TOOL_CALL_*` sequence. Parallel calls are declined because execution pauses at that boundary.

The client executes that call and starts another run containing the standard `role: "tool"` message with the matching `toolCallId`. Swaag accepts exactly the pending call, preserves content, error, metadata, message ID, request ID, and integrity-linked canonical history, then resumes the durable worker. Repeated historical tool messages must exactly match a known terminal call; unknown or altered messages fail rather than being ignored. Partial persistence and supervisor-restart windows reconstruct missing request/result history from the durable call store without duplicating events, while cancellation closes the pending call honestly.

The A2A projection accepts `send`, `get`, cursor-paginated `list`, `cancel`, and resumable `subscribe` operations. New sends create server-owned worker/context IDs; follow-up messages must cite a matching pair. Inline raw file parts enter the ordinary attachment store before execution, while URL parts remain disabled until an authenticated fetch capability exists. A send follows A2A's blocking default or returns the submitted task immediately when requested.

The communication listener serves the A2A 1.0 JSON-RPC binding on `/a2a/v1`, the HTTP+JSON binding on `/a2a/rest`, and the public Agent Card on `/.well-known/agent-card.json` without adding another state authority. JSON-RPC exposes the PascalCase task methods plus `Create/Get/List/DeleteTaskPushNotificationConfig` and `GetExtendedAgentCard`. HTTP+JSON exposes the corresponding message/task routes plus `/tasks/{taskId}/pushNotificationConfigs[/configId]` and `/extendedAgentCard`. Direct responses use protocol JSON shapes and `application/a2a+json`; direct streams contain unwrapped A2A stream responses. Both task streams and push delivery derive from the same durable worker events. Push callback credentials are AES-GCM encrypted at rest under an environment-supplied deployment key, callbacks are HTTPS-only and exact-host allowlisted, redirects are disabled, authentication header precedence matches the pinned official SDK, and delivery uses a durable bounded retry queue. Optional bearer authentication secures implemented A2A routes while leaving the well-known Agent Card public; configuration names the bearer secret environment variable and literal bearer secrets in TOML are rejected. Authenticated extended cards and ES256 Agent Card signing are implemented and tested. The pinned official `@a2a-js/sdk` 1.1.0 independently exercises task send/stream plus push create/get/list/delete and extended-card decoding over both JSON-RPC and HTTP+JSON with zero model-client access. gRPC and deployable OAuth/OIDC lifecycle remain separate work.

## Open WebUI Pipe

`integrations/open_webui_pipe.py` is a standalone Open WebUI Pipe for the localhost communication listener. It maps Open WebUI `chat_id` and `message_id` metadata through `open_webui.send` to durable conversation/worker and request/message rows, so retries and service restarts do not duplicate a known request. Each request records its initial event cursor before execution, including across retry replay. The Pipe follows progress through resumable `task.events.wait` cursors and drains bounded `open_webui.get` event pages before advancing. It returns final, failure, and blocking-question text directly instead of depending on a transient browser event connection; short `status` events are supplementary.

Open WebUI local file paths and image data URLs enter Swaag as raw content-addressed attachments with exact bytes and source lineage. The adapter does not extract them automatically. Non-local file/image references are described to the worker but are not fetched implicitly. Browser capabilities record protocol-independent `external_source_observed` history events, and the Pipe projects those integrity-linked events into persistence-safe Open WebUI `source` events with parallel document/metadata entries, URL, canonical history sequence/hash, and an explicit preview-reduction flag. Disabling supplementary status does not disable sources. Optional outbound text-artifact delivery is disabled by default and never exposes a local path. When explicitly configured, canonical artifact events produce persistent `files` events with an HMAC-signed expiring URL. The loopback listener verifies expiry, worker/session ownership, HMAC in constant time, and the artifact store's exact path/size/hash before returning `text/plain` with private/no-store, nosniff, and attachment-disposition headers. Non-loopback advertised URLs require HTTPS and the signing key comes from a named environment variable rather than durable config. Live acceptance remains blocked until an Open WebUI runtime is installed.

Task creation also accepts `completion_mode`: `natural` is the default terminal lifecycle, while `continuous` explicitly keeps semantically complete cycle results provisional and starts another context-compiled improvement cycle. Continuous workers stay in `working`, expose the latest provisional result and durable iteration events, and stop only through cancellation or a blocking LLM-authored question. Because they intentionally have no terminal completion point, they cannot declare a terminal caller output schema or presentation mode.

## Questions, provisional assumptions, and internal work

Questions are semantic control data. A blocking question carries no provisional assumption, must be disclosed verbatim to the user, and can put the worker into durable `input_required`. An optional question must carry a concrete `assumption_if_unanswered`; the exact question and exact assumption are mechanically required in the same user-facing assistant message so the user is told what the worker is assuming while work continues. Before asking, the model is instructed to inspect repository/environment state, documentation, research sources, other workers, and available tools when those can answer reliably.

General scratch computation, experiments, private notes, doability tests and downloaded knowledge belong in the configurable agent-owned data root through `agent_workspace`, not in the user project by default. Ordinary Python/shell operations are bubblewrap isolated with no network and no host/project visibility outside that root. Project-facing shell/terminal tools remain deliberately powerful and are a separate capability boundary.

Configuration precedence is mechanically `packaged defaults < project config/local.toml < explicit config_paths in caller order < SWAAG_CONFIG file < SWAAG__SECTION__KEY environment overrides`; each effective leaf records its winning source. Startup operations logs emit a redacted effective-config snapshot, fingerprint, source ledger and parameter metadata rather than relying on an undocumented merge order.

## Controls during active work

`message` appends the exact instruction to the worker's durable pending-control queue before attempting inference preemption. A model action is accepted only against the same ordered control snapshot from which it was compiled. A newer control invalidates a stale unexecuted action; a control delivered during a multi-tool action preserves completed tool evidence and abandons calls that have not started. Controls that arrive during independent completion evaluation, response presentation, caller-defined structured output, or the terminal commit boundary keep the candidate provisional and start another run cycle. The worker's `run_count` and `worker_control_continuation_started` events expose that continuation.

The runtime does not use keywords, source-specific priority, or deterministic conflict rules to decide what a control means. The next action prompt includes every pending control verbatim and in delivery order alongside the original objective and authoritative evidence. The LLM decides whether controls refine, replace, conflict with, or can be combined with prior intent; deterministic code owns only delivery order, stale-snapshot rejection, execution boundaries, persistence, cancellation, and terminal-state atomicity.

Worker inspection keeps semantic status separate from `mechanical_status`. The mechanical projection includes the validated active run phase/substate, semantic operation kind, active mechanical object, transition sequence and stage-entry timestamps, heartbeat time, synchronous wait state, running processes, pending controls, and pending durable wakeups plus `next_wakeup_at`. Context compilation distinguishes instruction resolution, prompt serialization, token measurement, and fit/overflow; output and tool-effect validation are separately visible. Blocking model and tool operations refresh the same heartbeat independently of model-authored status text.

Due wakeups enter the same exact pending-control queue. The communication service resolves the session's durable worker owner and moves an idle worker back through `queued` and `working`; it never runs the session behind the worker store. The standalone wakeup service uses the same worker-aware dispatcher and conflicts with the communication service so two process-local supervisors cannot race. Explicit worker cancellation cancels every still-scheduled or claimed wakeup after its durable lifecycle transition and records their IDs in a separate worker event.
