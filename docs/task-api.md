# Transport-neutral task API

`TaskApi` is the internal command/query boundary used by the communication service and protocol adapters. Worker state and events remain authoritative; transports do not own task lifecycle semantics.

## Caller-defined structured output

The `create` operation may include `output_schema` and `mechanical_fields`:

```json
{
  "objective": "Audit the release and report the finding.",
  "output_schema": {
    "type": "object",
    "properties": {
      "finding": {"type": "string"},
      "confidence": {"type": "string", "enum": ["low", "high"]},
      "worker": {"type": "string"},
      "state": {"type": "string", "enum": ["completed"]}
    },
    "required": ["finding", "confidence", "worker", "state"],
    "additionalProperties": false
  },
  "mechanical_fields": {
    "worker": "worker_id",
    "state": "status"
  },
  "start": true
}
```

Schemas must satisfy Swaag's portable closed-schema subset. Mechanical bindings address top-level output fields and may use `worker_id`, `session_id`, `objective`, `status`, `created_at`, `started_at`, or `run_count`. Those fields never enter the semantic generation schema. Remaining fields are generated by an LLM call that uses the central context compiler, actual schema-constrained decoding, full-fidelity evidence when it fits, and measured semantic tool-result reduction only on overflow.

The final merged object is mechanically validated against the caller's complete schema and stored in the terminal worker event. `get` returns it as `structured_output`. The ordinary textual worker `result` is always retained as the transport-independent common-denominator response.

## Optional response presentations

Task creation may include `"presentation_modes": ["visual", "audio"]`. This is opt-in: an omitted or empty array adds no presentation model calls and leaves the verified worker result unchanged. `visual` runs a separately context-compiled semantic relevance editor over the exact worker result. `audio` first uses that selected user-facing information, then runs a different context-compiled transformation for listenable prose. An independent constrained model call compares each candidate with the exact source and user request; rejected candidates receive bounded evidence-based repair, and an unverified candidate is never reported as completed.

The raw worker result remains `result`. Successful or unavailable variants, exact source/output hashes, evaluations, attempts, and failures are durable history/worker events, while `get` and task-create/start responses expose the terminal `presentations` object. Continuous workers reject terminal presentation modes because they intentionally have no final response boundary. The default remains disabled until live one-call/staged and small-model experiments justify a deployment policy.

Run the checkpointed live comparison with `python -m swaag.benchmark response-presentation --output /data/var/swaag/benchmarks/response-presentation`. Repeat with `--model-base-url` for an alternate small-model or device endpoint; results retain each model-call kind, context compilation, independent evaluation, latency, and exact rendered answer.

Status questions use a separate context-compiled operation over exact worker events and mechanical state. When `communication.model_base_url` selects a separate runtime, its constrained status output can request stronger interpretation. Swaag then sends the unchanged evidence snapshot to the main runtime at communication priority and records integrity-linked escalation request, resolution or failure events. Run `python -m swaag.benchmark communication-routing --assistant-model-base-url URL --output /data/var/swaag/benchmarks/communication-routing` before relying on a smaller model in production.

## Durable event cursors

`events` returns worker events after `after_sequence` with a bounded `limit`. `events.wait` uses the same cursor and waits up to 60 seconds for a new event or an input-required/terminal state; its `timed_out` and `terminal` fields distinguish those outcomes. Reissuing the request with `next_sequence` is resumable and does not depend on a live connection.

Worker lifecycle rows stay small. Stream-worthy canonical session events are linked by session ID, sequence, event ID, type, and integrity hash. A read hydrates the exact append-only source event on demand and rejects a mismatched reference; raw tool results and semantic status are therefore not copied into a second authority. The AG-UI view maps linked tool calls/results, semantic status, questions, and assistant progress into protocol events. `ag_ui.subscribe` remains the transport-neutral bounded cursor wait used beneath richer adapters.

The same listener now accepts a standard AG-UI `RunAgentInput` as `POST /ag-ui` and returns unwrapped AG-UI events over `text/event-stream`. The client-owned `threadId` maps durably to one worker and each `runId` maps to exact worker-event start/end cursors, allowing an idempotent retry to replay that run without starting it twice. A newer run closes the previous stream boundary; replay reports a superseded run honestly instead of assigning later events to the old run ID. The stream starts with the supplied thread/run IDs, follows canonical worker events without holding inference admission, and closes on success, failure, cancellation, or a resumable interrupt.

`GET /ag-ui/capabilities` returns the current official `AgentCapabilities` shape. It derives the backend-tool inventory and exact input schemas from the effective runtime registry, reports the configured action bound, and declares only implemented protocol behavior. SSE streaming, state snapshots, state persistence within a thread, resumable human interrupts, and sequential client-provided tools are supported. State deltas, WebSocket, binary HTTP, push delivery, sequence-number stream resume, parallel calls, and AG-UI caller-defined structured output remain explicitly false. The response is dynamic and `no-store`; unsupported methods fail with `405` rather than being mistaken for a run request.

For a new thread, the complete supplied textual conversation seeds the durable objective. Later runs add the current user request. Typed inline AG-UI image/audio/video/document data and legacy binary data enter raw attachment storage; URL/reference inputs are disclosed to the worker but never fetched implicitly. Caller context is preserved. Every accepted run binds an exact append-only shared-state revision to its run ID, includes that current state with hash/revision provenance in the worker's ordinary full-fidelity context, and emits the same value as `STATE_SNAPSHOT`; retry replay cannot replace the state originally bound to a run. An omitted state inherits the last accepted thread revision. Agent-authored state changes and RFC 6902 deltas are not yet implemented and are declared false. Forwarded props still fail explicitly because silently discarding them would be incorrect. A `resume` entry must address the exact durable open interrupt ID; resolved payloads become user input and canceled responses use normal worker cancellation.

`RunAgentInput.tools` may define client-executed capabilities using Swaag's portable closed JSON-schema subset. A run binds the exact catalog, metadata, hash, source thread, and run ID as a durable revision. Catalog names cannot shadow any server capability. Client tools enter the same compact capability index and staged schema-selection path as server tools, so semantic selection remains model-owned and exact schemas consume context only when selected. A selected client call is validated and persisted with exact arguments and lineage, then the worker enters a distinct client-execution wait and the AG-UI run ends successfully after emitting the ordinary `TOOL_CALL_*` sequence. Parallel calls are declined because execution pauses at that boundary.

The client executes that call and starts another run containing the standard `role: "tool"` message with the matching `toolCallId`. Swaag accepts exactly the pending call, preserves content, error, metadata, message ID, request ID, and integrity-linked canonical history, then resumes the durable worker. Repeated historical tool messages must exactly match a known terminal call; unknown or altered messages fail rather than being ignored. Partial persistence and supervisor-restart windows reconstruct missing request/result history from the durable call store without duplicating events, while cancellation closes the pending call honestly.

The A2A projection accepts `send`, `get`, cursor-paginated `list`, `cancel`, and resumable `subscribe` operations. New sends create server-owned worker/context IDs; follow-up messages must cite a matching pair. Inline raw file parts enter the ordinary attachment store before execution, while URL parts remain disabled until an authenticated fetch capability exists. A send follows A2A's blocking default or returns the submitted task immediately when requested.

The communication listener also serves the A2A 1.0 JSON-RPC binding on `/a2a/v1`, the HTTP+JSON binding on `/a2a/rest`, and the required public Agent Card on `/.well-known/agent-card.json`, without adding another port or state authority. JSON-RPC exposes the PascalCase methods; HTTP+JSON exposes `POST /message:send`, `POST /message:stream`, `GET /tasks`, `GET /tasks/{id}`, `POST /tasks/{id}:cancel`, and `POST /tasks/{id}:subscribe` relative to its advertised base. The current prose specification and official JavaScript SDK 1.1.0 use POST for subscription while the checked-in 1.0 proto annotation uses GET, so Swaag accepts both bodyless forms. Direct responses use protocol JSON shapes and `application/a2a+json`; direct streams contain unwrapped A2A stream responses. Get/list history limits project exact append-only user/assistant message events with source sequence/hash provenance; list filtering, pagination, and optional artifact inclusion follow the current protocol bounds. Both bindings atomically capture the initial durable task plus event cursor for streams, then emit only later status/artifact updates until terminal state. HTTP requests require `A2A-Version: 1.0`, bounded headers/bodies, and exact content types; HTTP+JSON errors use `google.rpc.Status` JSON with protocol error details. Because no transport authentication exists, the listener mechanically rejects non-loopback binds rather than relying only on deployment convention. Authenticated non-local exposure, gRPC, push-notification configuration, and signed/extended Agent Cards remain separate work.

## Open WebUI Pipe

`integrations/open_webui_pipe.py` is a standalone Open WebUI Pipe for the localhost communication listener. It maps Open WebUI `chat_id` and `message_id` metadata through `open_webui.send` to durable conversation/worker and request/message rows, so retries and service restarts do not duplicate a known request. Each request records its initial event cursor before execution, including across retry replay. The Pipe follows progress through resumable `task.events.wait` cursors and drains bounded `open_webui.get` event pages before advancing. It returns final, failure, and blocking-question text directly instead of depending on a transient browser event connection; short `status` events are supplementary.

Open WebUI local file paths and image data URLs enter Swaag as raw content-addressed attachments with exact bytes and source lineage. The adapter does not extract them automatically. Non-local file/image references are described to the worker but are not fetched implicitly. Browser capabilities record protocol-independent `external_source_observed` history events, and the Pipe projects those integrity-linked events into persistence-safe Open WebUI `source` events with parallel document/metadata entries, URL, canonical history sequence/hash, and an explicit preview-reduction flag. Disabling supplementary status does not disable sources. Outbound downloadable files require a safe authenticated artifact-serving contract and remain unimplemented rather than emitting unusable local paths. Live acceptance also remains blocked until an Open WebUI runtime is installed.

Task creation also accepts `completion_mode`: `natural` is the default terminal lifecycle, while `continuous` explicitly keeps semantically complete cycle results provisional and starts another context-compiled improvement cycle. Continuous workers stay in `working`, expose the latest provisional result and durable iteration events, and stop only through cancellation or a blocking LLM-authored question. Because they intentionally have no terminal completion point, they cannot declare a terminal caller output schema or presentation mode.

## Controls during active work

`message` appends the exact instruction to the worker's durable pending-control queue before attempting inference preemption. A model action is accepted only against the same ordered control snapshot from which it was compiled. A newer control invalidates a stale unexecuted action; a control delivered during a multi-tool action preserves completed tool evidence and abandons calls that have not started. Controls that arrive during independent completion evaluation, response presentation, caller-defined structured output, or the terminal commit boundary keep the candidate provisional and start another run cycle. The worker's `run_count` and `worker_control_continuation_started` events expose that continuation.

The runtime does not use keywords, source-specific priority, or deterministic conflict rules to decide what a control means. The next action prompt includes every pending control verbatim and in delivery order alongside the original objective and authoritative evidence. The LLM decides whether controls refine, replace, conflict with, or can be combined with prior intent; deterministic code owns only delivery order, stale-snapshot rejection, execution boundaries, persistence, cancellation, and terminal-state atomicity.

Worker inspection keeps semantic status separate from `mechanical_status`. The mechanical projection includes the validated active run phase/substate, semantic operation kind, active mechanical object, transition sequence and stage-entry timestamps, heartbeat time, synchronous wait state, running processes, pending controls, and pending durable wakeups plus `next_wakeup_at`. Context compilation distinguishes instruction resolution, prompt serialization, token measurement, and fit/overflow; output and tool-effect validation are separately visible. Blocking model and tool operations refresh the same heartbeat independently of model-authored status text.

Due wakeups enter the same exact pending-control queue. The communication service resolves the session's durable worker owner and moves an idle worker back through `queued` and `working`; it never runs the session behind the worker store. The standalone wakeup service uses the same worker-aware dispatcher and conflicts with the communication service so two process-local supervisors cannot race. Explicit worker cancellation cancels every still-scheduled or claimed wakeup after its durable lifecycle transition and records their IDs in a separate worker event.
