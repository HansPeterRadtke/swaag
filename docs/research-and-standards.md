# Research and standards notes

External work informs Swaag but is not architectural authority. Re-check versions and specifications before implementation because these projects evolve quickly.

Anthropic's context-engineering work treats context as a finite resource curated for every inference from instructions, tools, external data, and history. Letta similarly treats context management as a central harness responsibility. Recent externalized-history work such as Scroll explores keeping lossless events outside the prompt and projecting selected information into working context. Preserve authoritative source state outside context and benchmark compaction rather than copying one memory framework.

Liu et al.'s primary *Lost in the Middle* study found position-sensitive, often U-shaped retrieval behavior: changing only where relevant evidence appears can materially change accuracy. RULER shows why a single needle-retrieval pass is insufficient by adding multiple retrieval, tracing, aggregation, and question-answering tasks and measuring degradation as length and complexity rise. Swaag therefore keeps two model-specific live probes: repeated early/middle/late single-fact retrieval across utilization levels, and balanced cyclic layouts that move actual task, current-request, history, tool-definition, tool-result, and retrieved-evidence sections through every user-context position. These are diagnostics, not a deterministic production ordering policy, and later work still needs multi-hop/aggregation coverage: <https://arxiv.org/abs/2307.03172> and <https://arxiv.org/abs/2404.06654>.

Relevant evaluation families include FollowBench for multi-constraint instruction following, AgentIF and AgentIF-OneDay for agentic instruction following, OR-Bench for unnecessary refusal, and long-horizon benchmarks for persistence and premature completion. Prompt optimization systems such as Promptfoo illustrate a useful baseline/variant/held-out-evaluation workflow. Keep prompt evaluation model-specific.

AG-UI defines rich streamed agent-to-UI events. A2A defines durable task-oriented interoperability including long-running task states. Open WebUI exposes status/progress, user input and confirmation, files, citations, and custom events and can be supported through an adapter. MCP is useful for capability discovery and structured tools. These solve different layers; keep Swaag's internal event/state model transport-independent.

Rechecked on 2026-08-26 against primary specifications:

- AG-UI's current `HttpAgent` posts `RunAgentInput` and consumes an unwrapped `BaseEvent` SSE stream. The event model requires one stable client `runId` across a run, represents normal completion with a success outcome, and represents durable human-input pauses with a non-empty interrupt outcome whose ID is addressed by a later `resume` entry. Tool streaming uses `TOOL_CALL_START`, argument deltas, `TOOL_CALL_END`, and `TOOL_CALL_RESULT`. It has no dedicated run-canceled event, so Swaag projects cancellation as a named custom event plus a coded run error rather than pretending completion. Typed multimodal inputs use inline base64 `data` or URL sources. Swaag now serves this HTTP/SSE shape while retaining durable event cursors underneath; shared state, client-side tool execution, binary transport, WebSocket, and capability discovery remain explicit gaps: <https://docs.ag-ui.com/sdk/js/client/http-agent>, <https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/concepts/events.mdx>, and <https://docs.ag-ui.com/sdk/js/core/multimodal-inputs>.
- A2A 1.0 defines submitted, working, input-required, auth-required, completed, failed, canceled, and rejected task states plus send/get/list/cancel/subscribe operations. Send is blocking by default unless `returnImmediately` is true; task IDs are server-owned; a supplied task/context pair must match; and a subscription starts with the current Task, streams status/artifact updates, rejects already-terminal tasks, and closes at terminal state. Its JSON-RPC binding uses PascalCase methods over HTTP, `A2A-Version: 1.0`, and SSE for `SendStreamingMessage`/`SubscribeToTask`; discovery uses `/.well-known/agent-card.json` with cache validators. Swaag maps only states with matching semantics, keeps archive as metadata rather than inventing an A2A state, and now serves that JSON-RPC/SSE binding on the existing localhost communication listener: <https://github.com/a2aproject/A2A/blob/main/docs/specification.md> and <https://github.com/a2aproject/A2A/blob/main/specification/a2a.proto>.
- Open WebUI persists only selected short event names such as `status`, `message`, `files`, and `source`; interactive `input`/`confirmation` depends on a live bidirectional connection, and Pipe final content must use the return/yield channel. A persistence-safe `source` carries parallel `document` and `metadata` arrays plus a source identity, while `files` requires a URL that the UI can actually fetch. Pipe reserved arguments provide stable chat/message metadata and uploaded-file metadata; local uploads can expose a server path while image content may arrive as data URLs. Swaag's Pipe therefore returns critical text normally, preserves local/data-URL bytes as raw attachments, maps canonical browser evidence to `source`, and neither turns remote references into implicit fetches nor invents downloadable URLs for private local artifacts: <https://docs.openwebui.com/features/extensibility/plugin/development/events/> and <https://docs.openwebui.com/features/extensibility/plugin/function/>.
- MCP 2026-07-28 remains a model-controlled tool/capability protocol and now requires request `_meta` protocol/client fields, discovery, and explicit cache hints on list results. Invalid tool names/arguments are protocol errors while failures during valid tool execution are successful JSON-RPC responses with `isError: true`; Swaag preserves that distinction. MCP is not Swaag's task lifecycle: <https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx>.

Docling is a strong broad document conversion/extraction system. Jetson also has the separate all2text project with multiple format-specific and provider-backed conversion paths. Neither is a universal semantic ingestion standard. Preserve raw files and let an LLM choose whether and how to inspect them based on user intent.

llama.cpp supports continuous batching and parallel serving configurations, but cancellation/preemption behavior must be tested for the deployed version. vLLM provides alternative scheduling mechanisms. Swaag's runtime abstraction should be stronger than any backend and must not claim true suspend/resume unless the backend actually provides it.

The current llama.cpp server documents `GET /props` `total_slots` as the process request-slot count and `GET /slots` as its per-slot monitoring view. Swaag uses `total_slots` only as a mechanical admission capacity and keeps scheduling/lifecycle state backend-neutral; it does not infer semantic importance from backend data: <https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md>.

The same primary llama.cpp server documentation defines `POST /apply-template` as the non-inference operation that converts `/v1/chat/completions`-style messages into the exact string expected by the active model and explicitly documents sending that returned prompt to `/completion`. `GET /props` exposes the active `chat_template` and model path, and the current server also exposes chat input-token endpoints. A local 2026-08-26 probe against the Jetson Qwen2.5 server confirmed that `/apply-template` returns Qwen ChatML framing rather than the Llama-3 markers Swaag previously hardcoded. Swaag therefore keeps role/content prompt construction model-neutral, delegates live llama.cpp serialization to `/apply-template`, hashes the complete model/template identity, and rejects identity changes before generation. Remote OpenAI-compatible providers still need provider-specific capacity and serialization-accounting discovery rather than pretending a local template is authoritative: <https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md> and <https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server.cpp>.

OpenTelemetry has GenAI semantic conventions for model, agent, and tool telemetry. Prefer those conventions for operational traces and metrics while keeping telemetry distinct from durable semantic execution history.

Rechecked on 2026-08-26 against the current OpenTelemetry GenAI repository and Python guidance:

- GenAI inference spans represent a logical operation, including automatic retries, use `CLIENT` for an out-of-process model server, and require `gen_ai.operation.name` plus `gen_ai.provider.name`. Agent invocation and agent-side tool execution use the current `invoke_agent` and `execute_tool` conventions. These conventions remain Development, so keep the mapping isolated and version-conscious: <https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md> and <https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md>.
- Current metrics include `gen_ai.client.operation.duration`, `gen_ai.client.token.usage`, `gen_ai.invoke_agent.duration`, and `gen_ai.execute_tool.duration`. Token usage must not be invented when it cannot be obtained efficiently; Swaag uses backend counts or its exact tokenizer-backed input count and omits unavailable estimates: <https://github.com/open-telemetry/semantic-conventions-genai/blob/main/model/gen-ai/metrics.yaml>.
- Prompt, message, tool-argument, and tool-result content is sensitive opt-in data. Swaag's default instrumentation emits mechanical identifiers/accounting only, not semantic content. The package depends on the OpenTelemetry API, while SDK/exporter/provider configuration belongs to the hosting application as recommended for instrumented libraries: <https://opentelemetry.io/docs/languages/python/instrumentation/>.

- The current GenAI metrics define client operation duration/token usage and server duration/first-token/per-token timing, but not a stable queue-depth or queue-wait convention. Queue/KV-cache/prefill metrics remain an open proposal. Swaag therefore keeps its admission measurements under the explicit `swaag.inference.*` namespace rather than mislabeling client-side scheduler data as standardized server telemetry: <https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md> and <https://github.com/open-telemetry/semantic-conventions-genai/issues/87>.

When a design task says to research an open question, actually search documentation, specifications, papers, implementations, and the local machine where relevant; compare alternatives; perform safe experiments; and record what passed, failed, and remains uncertain. Do not convert an open research instruction into an unsupported architectural assertion.

Swaag's browser capabilities are availability-gated mechanical tools, not deterministic research routing. Search and page calls expose bounded structured previews, but every call stores the exact raw provider response and diagnostics as integrity-checked artifacts with hashes and canonical tool-result lineage. The LLM decides when research is valuable and when a raw artifact needs targeted re-expansion. A live Jetson smoke test on 2026-08-26 successfully queried DuckDuckGo through the local aubro backend and recovered the exact response through Swaag's artifact store.
