# Research and standards notes

External work informs Swaag but is not architectural authority. Re-check versions and specifications before implementation because these projects evolve quickly.

Anthropic's context-engineering work treats context as a finite resource curated for every inference from instructions, tools, external data, and history. Letta similarly treats context management as a central harness responsibility. Recent externalized-history work such as Scroll explores keeping lossless events outside the prompt and projecting selected information into working context. Preserve authoritative source state outside context and benchmark compaction rather than copying one memory framework.

Liu et al.'s primary *Lost in the Middle* study found position-sensitive, often U-shaped retrieval behavior: changing only where relevant evidence appears can materially change accuracy. RULER shows why a single needle-retrieval pass is insufficient by adding multiple retrieval, tracing, aggregation, and question-answering tasks and measuring degradation as length and complexity rise. Swaag therefore keeps two model-specific live probes: repeated early/middle/late single-fact retrieval across utilization levels, and balanced cyclic layouts that move actual task, current-request, history, tool-definition, tool-result, and retrieved-evidence sections through every user-context position. These are diagnostics, not a deterministic production ordering policy, and later work still needs multi-hop/aggregation coverage: <https://arxiv.org/abs/2307.03172> and <https://arxiv.org/abs/2404.06654>.

Relevant evaluation families include FollowBench for progressively composed content/situation/style/format/example constraints, AgentIF for long instructions and tool/conditional constraints, AgentIF-OneDay for end-to-end work, OR-Bench for unnecessary refusal, and long-horizon benchmarks for persistence and premature completion. The newer HANDBOOK.md benchmark is especially relevant to durable standing instructions: even its best reported configuration passed only 36.2% of complete policy-governed tasks, with failures including overriding standing policy, acting against a check result, losing rules over long horizons, and falsely reporting compliance. Swaag's checkpointed `instruction-following` probe therefore reports both per-constraint success (CSR-like) and strict all-constraints-per-case success (ISR-like), separates baseline from held-out policies, runs through the production compiler/tool loop, and retains exact instruction/context provenance. It is a small diagnostic, not a substitute for importing licensed upstream suites. Prompt optimization systems such as APO and Promptbreeder show that model-authored prompt revision can improve measured task performance, while reported OPRO failures on smaller models warn against trusting self-optimization without held-out, model-specific evaluation. Primary sources: <https://arxiv.org/abs/2310.20410>, <https://arxiv.org/abs/2505.16944>, <https://arxiv.org/abs/2601.20613>, <https://arxiv.org/abs/2607.25398>, <https://arxiv.org/abs/2305.03495>, <https://arxiv.org/abs/2309.16797>, and <https://arxiv.org/abs/2405.10276>.

Durable instruction distillation has related evidence but no universal safe recipe. MemPrompt demonstrates that recorded user corrections can repair later prompting without retraining. The August 2026 Agent Memory Distillation study reports strong gains when a capable teacher separates successful experience into workflow, subtask, and function-level memories, but also finds that flat transfer can degrade some students and that teacher/student compatibility matters. MePO likewise reports that instruction-heavy prompts from stronger models can overwhelm lightweight models. MEMDRIFT adds a different failure mode: memories that are useful in one semantic setting can bias unrelated tool parameters, and ordinary relevance prompting does not eliminate the effect. Swaag therefore keeps exact correction sources recoverable, makes the LLM author and scope durable instructions through the generic worker/tool path, forbids deterministic transcript parsing or keyword scope assignment, and treats duplicate repair, category isolation, small-model compatibility, and held-out downstream behavior as required evaluations rather than assuming that more memory is better. Primary sources: <https://aclanthology.org/2022.emnlp-main.183/>, <https://arxiv.org/abs/2608.07169>, <https://aclanthology.org/2026.eacl-long.38/>, and <https://arxiv.org/abs/2605.24941>.

Recent learned-memory systems strengthen the case for model-owned lifecycle and state-specific applicability, but do not justify a deterministic semantic router. Memory-R1 trains separate manager and answer policies for ADD/UPDATE/DELETE/NOOP and relevant-entry selection. AgeMem exposes store, retrieve, update, summarize, and discard operations directly to the agent policy. SAMem reports that state-aligned fine-grained retrieval outperforms coarse task-level memory in its decision benchmarks, while HiGMem uses LLM-guided semantic anchors rather than placing a flat memory bank into every prompt. Conversely, the 2026 experience-following study shows that retrieved mistakes and superficially similar but misaligned experiences can propagate into future output. Swaag therefore uses mechanically validated broad instruction scopes and storage bounds, but gives LLMs the exact next-call context and candidate instructions or working notes for semantic category/relevance selection; uncertain failure conservatively includes all exact candidates. Notes expose model-owned add/replace/remove/consolidate operations and remain recoverable event sources. Required evaluations include category isolation, prompt bloat, incorrect-memory propagation, lifecycle edits, and held-out downstream behavior across model sizes. Primary sources: <https://aclanthology.org/2026.acl-long.583/>, <https://aclanthology.org/2026.acl-long.981/>, <https://aclanthology.org/2026.findings-acl.722/>, <https://aclanthology.org/2026.findings-acl.1690/>, and <https://aclanthology.org/2026.acl-long.27/>.

## DRT, provenance, and KnowMoreDiRT

The August 25 recording asks whether Discourse Representation Theory (DRT) and the local KnowMoreDiRT project could eventually improve durable knowledge and reasoning. DRT is relevant, but it is not a ready-made agent-memory architecture. Classical DRT models meaning as a context update over discourse referents, conditions, scope, and accessibility. Segmented DRT adds rhetorical discourse structure and explicitly separates constructing a logical form from evaluating it. Boxer and the Parallel Meaning Bank demonstrate that machine-readable DRSs can support broad semantic parsing, but they also use substantial parsing pipelines, controlled representations, lexical resources, and manual or benchmark evaluation. The DRS parsing shared task emphasizes that explicit scope, shared variables, negation, modality, quantification, and presupposition make even sentence-level DRS construction difficult. Primary sources: <https://www.ims.uni-stuttgart.de/archiv/kamp/files/2011.kamp.van.genabith.reyle.discourse.representation.theory.pdf>, <https://aclanthology.org/W08-2222/>, <https://aclanthology.org/W19-1201/>, and <https://arxiv.org/abs/1702.03964>.

The local `/data/src/github/KnowMoreDiRT` repository was audited read-only on 2026-08-27 at commit `9385bdd`. Its useful foundations are a deliberately small raw-folder API, exact source spans, normalized SQLite records for referents/contexts/conditions, model-output schemas, grounding checks, and provenance. Its current production answer path is not suitable for reuse as Swaag's general semantic layer. `engine.py` routes through many source- and question-shaped deterministic handlers before and after the model, including special paths for review/approval actors, owner fields, commit hashes, correction clauses, table statuses, actor IDs, and reference chains. Some vocabulary is assembled from string fragments, which lets literal-only architecture scans pass without removing the semantic branch. `query.py` still contains deterministic question-word answer typing and domain noun maps, while `bounded_dspg.py` contains thousands of lines of lexical matching and answer-shape policy. The repository's own documentation acknowledges that the clean model-centered path is incomplete and that self-written fixture scores do not establish generalization. A no-model run passed all 384 tests, including 380 unit/smoke tests, the anti-hardcode checks, and all four self-written fixture gates, but that result demonstrates the limits of those checks rather than proving a clean generic architecture.

If Swaag experiments with DRT/DSPG later, it should do so as a replaceable, derived semantic index over authoritative history and artifacts, never as a replacement for them. LLM calls should author referents, conditions, scope, uncertainty, identity hypotheses, and relevance; deterministic code may validate schemas, IDs, exact source grounding, graph integrity, accessibility mechanics, and provenance. Every derived object must retain immutable source references and be rebuildable or removable when its source changes. Contradictions and unresolved identity must remain represented rather than being collapsed into one asserted fact. The context compiler may then ask an LLM to select or project relevant graph/source material under measured pressure, with exact re-expansion still available.

Adoption requires held-out and mutation-based evaluation, not recovery of visible fixtures: raw-folder and durable-history rebuilds, paraphrased questions, renamed entities and relations, temporal revision, scoped belief/report/negation, contradiction and unknown handling, multi-hop retrieval, provenance reconstruction, source deletion/update, and latency/storage measurements. It should be attempted only after the fundamental context, lifecycle, and evidence harness remains stable. The current KnowMoreDiRT implementation should inform those experiments and failure cases, but must not be imported as Swaag production reasoning code.

AG-UI defines rich streamed agent-to-UI events. A2A defines durable task-oriented interoperability including long-running task states. Open WebUI exposes status/progress, user input and confirmation, files, citations, and custom events and can be supported through an adapter. MCP is useful for capability discovery and structured tools. These solve different layers; keep Swaag's internal event/state model transport-independent.

Rechecked on 2026-08-28 against primary specifications:

- AG-UI's current `HttpAgent` posts `RunAgentInput` and consumes an unwrapped `BaseEvent` SSE stream. The event model requires one stable client `runId` across a run, represents normal completion with a success outcome, and represents durable human-input pauses with a non-empty interrupt outcome whose ID is addressed by a later `resume` entry. Tool streaming uses `TOOL_CALL_START`, argument deltas, `TOOL_CALL_END`, and `TOOL_CALL_RESULT`. Client-provided tools travel in `RunAgentInput.tools`; the client assembles the streamed assistant tool call, executes it, and supplies a standard `role: "tool"` message with `toolCallId` on its next run. Swaag follows that boundary with exact run-bound catalogs, staged schema discovery, one durable pending call, exact result lineage, and no parallel-call claim. The pinned official client completed this two-run flow without inference and did not require a private event shape. AG-UI has no dedicated run-canceled event, so Swaag projects cancellation as a named custom event plus a coded run error rather than pretending completion. Typed multimodal inputs use inline base64 `data` or URL sources. Shared state is bidirectional protocol data: a run supplies current state, snapshots replace the complete client state, and deltas are ordered RFC 6902 updates that clients apply atomically. Swaag preserves every accepted client baseline and agent patch as an exact append-only revision. A runtime-bound, semantically selected tool exposes full reads and optimistic revision/hash-guarded RFC 6902 mutation; deterministic code owns only patch validity, conflicts, serialization, hashes, persistence, and provenance. The official 0.0.59 client applied the resulting real `STATE_DELTA` to a nested non-empty snapshot with zero model-client access. Python `jsonpatch` 1.33 is a stable modified-BSD RFC 6902 implementation and avoids a private partial patch interpreter; RFC 6901 remains the pointer syntax authority. The official `AgentCapabilities` schema is optional discovery data, and integration implementations place it beside the run endpoint, so Swaag exposes its runtime-derived declaration at `GET /ag-ui/capabilities`; the pinned core schema accepts the complete response. WebSocket must not be inferred merely because the schema has a `websocket` flag: the protocol repository still describes transport semantics in an open proposal and explicitly tracks the absence of a production integration. Swaag therefore advertises it as false instead of implementing an unstable private dialect: <https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/sdk/js/client/abstract-agent.mdx>, <https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/concepts/capabilities.mdx>, <https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/concepts/events.mdx>, <https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/concepts/state.mdx>, <https://datatracker.ietf.org/doc/html/rfc6902>, <https://datatracker.ietf.org/doc/html/rfc6901>, <https://pypi.org/project/jsonpatch/1.33/>, <https://docs.ag-ui.com/sdk/js/core/multimodal-inputs>, <https://github.com/ag-ui-protocol/ag-ui/issues/2084>, <https://github.com/ag-ui-protocol/ag-ui/issues/2162>, and <https://www.npmjs.com/package/@ag-ui/client/v/0.0.59>.
- A2A 1.0 defines submitted, working, input-required, auth-required, completed, failed, canceled, and rejected task states plus send/get/list/cancel/subscribe operations. Send is blocking by default unless `returnImmediately` is true; task IDs are server-owned; a supplied task/context pair must match; and a subscription starts with the current Task, streams status/artifact updates, rejects already-terminal tasks, and closes at terminal state. Its JSON-RPC binding uses PascalCase methods over HTTP; HTTP+JSON uses resource-oriented routes and `google.rpc.Status` JSON errors; both use `A2A-Version: 1.0` and SSE for streaming. Discovery uses `/.well-known/agent-card.json` with cache validators. Swaag maps only states with matching semantics and keeps archive as metadata rather than inventing an A2A state. The current official `@a2a-js/sdk` 1.1.0 client resolves Swaag's real Agent Card, selects either advertised A2A 1.0 JSON-RPC or HTTP+JSON transport, validates list/get/cancel decoding, creates server-owned tasks through unary and streaming send, and consumes initial-task-first streams through terminal cancellation and clean close. The prose specification and SDK use `POST /tasks/{id}:subscribe`, while the checked-in 1.0 proto annotates that operation as GET; Swaag accepts both bodyless forms instead of assuming those primary artifacts agree. Both new-task probes use a queue-only service with a client that raises on model access and record zero accesses, isolating protocol behavior rather than inference. This is not evidence for the still-missing gRPC, push-notification, authenticated extended-card, or signing paths: <https://a2a-protocol.org/dev/specification/>, <https://github.com/a2aproject/A2A/blob/main/specification/a2a.proto>, and <https://www.npmjs.com/package/@a2a-js/sdk/v/1.1.0>.
- Open WebUI persists only selected short event names such as `status`, `message`, `files`, and `source`; interactive `input`/`confirmation` depends on a live bidirectional connection, and Pipe final content must use the return/yield channel. A persistence-safe `source` carries parallel `document` and `metadata` arrays plus a source identity, while `files` requires a URL that the UI can actually fetch. Pipe reserved arguments provide stable chat/message metadata, uploaded-file metadata, and the raw FastAPI `__request__` object; local uploads can expose a server path while image content may arrive as data URLs. Swaag's Pipe therefore returns critical text normally, preserves local/data-URL bytes as raw attachments, forwards only W3C fields from `__request__.headers`, maps canonical browser evidence to `source`, and neither turns remote references into implicit fetches nor invents downloadable URLs for private local artifacts: <https://docs.openwebui.com/features/extensibility/plugin/development/events/>, <https://docs.openwebui.com/features/extensibility/plugin/development/reserved-args/>, and <https://docs.openwebui.com/features/extensibility/plugin/functions/pipe/>.
- MCP 2026-07-28 remains a model-controlled tool/capability protocol. Every request requires `_meta` protocol version and per-request client capabilities; `clientInfo` is a SHOULD rather than a MUST, but a supplied identity must contain the schema's `name` and `version`. The stateless revision requires `server/discover`, server identity in response `_meta`, and explicit cache hints on cacheable results. Invalid tool names/arguments are protocol errors while failures during valid tool execution are successful JSON-RPC responses with `isError: true`; Swaag preserves that distinction. The stable official TypeScript client 2.0.0 validates the real Swaag stdio and Streamable HTTP paths under a pinned modern-era negotiation, including discovery, complete list decoding, structured tool calls, mirrored `x-mcp-header` parameters, and the 2026-07-28 `subscriptions/listen` lifecycle. An inference-forbidden ephemeral service let the official SDK acknowledge `{toolsListChanged:true}`, receive `notifications/tools/list_changed` carrying `io.modelcontextprotocol/subscriptionId` after an in-memory catalog revision, and close the subscription locally. That validates the implemented change-notification transport without turning MCP into Swaag's task lifecycle. The 2026-07-28 MRTR migration guidance confirms that server→client request pushes are removed for modern connections: tools/prompts/resources return `input_required`, the client fulfills embedded elicitation/sampling/roots requests, and retries the original call with bare `inputResponses`, byte-exact opaque `requestState`, and a fresh request ID. Swaag implements this only through an explicit MCP per-tool hook that either requests input or returns canonical tool arguments; ordinary tools reject retry fields and final execution still uses the normal authorized registry. The pinned official client auto-fulfilled one elicitation and completed the retried calculator call without inference. For remote authorization, the current MCP authorization specification requires the MCP server to act as an OAuth protected resource, publish RFC 9728 metadata, accept bearer tokens only in the Authorization header, validate tokens for the exact resource/audience, and return standards-shaped `WWW-Authenticate` challenges; the 2026-07-28 revision further hardens client issuer handling and moves registration toward CIMD. Swaag now implements the resource-server side using OAuth token introspection with exact audience/scope checks and an explicit browser-origin allowlist. The dedicated MCP-only socket deliberately stays loopback-only because this raw server does not terminate TLS; remote deployment must use a TLS reverse proxy, which avoids exposing the multiplexed A2A/AG-UI communication listener or transmitting bearer tokens over plaintext. Live real-provider/TLS-proxy acceptance remains separate work: <https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts>, <https://github.com/modelcontextprotocol/typescript-sdk/releases/tag/v2.0.0>, <https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/discover.mdx>, <https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx>, and <https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http>.

Docling is a strong broad document conversion/extraction system. Jetson also has the separate all2text project with multiple format-specific and provider-backed conversion paths. Neither is a universal semantic ingestion standard. Preserve raw files and let an LLM choose whether and how to inspect them based on user intent. The local all2text CLI contract provides a no-file `--capabilities` probe with exact library, executable, provider, and provider-family states. Swaag exposes that probe as a staged capability, not an automatic routing rule. A 2026-08-28 production-path smoke test against `/data/venv/bin/all2text` preserved the exact 176,306-character response (`dd88a304e77a054d51dcbcc4a6e30373ceefd69a711a8e5815e28fc61a48f7cf`) and projected all 14 provider statuses and all 53 provider-family statuses. The complete run evidence is under `/data/var/swaag/manual-tests/attachment-capabilities-20260828T023257`; this establishes current host discovery, not specialist extraction quality.

llama.cpp supports continuous batching and parallel serving configurations, but cancellation/preemption behavior must be tested for the deployed version. vLLM provides alternative scheduling mechanisms. Swaag's runtime abstraction should be stronger than any backend and must not claim true suspend/resume unless the backend actually provides it.

The current llama.cpp server documents `GET /props` `total_slots` as the process request-slot count and `GET /slots` as its per-slot monitoring view. Swaag uses `total_slots` only as a mechanical admission capacity and keeps scheduling/lifecycle state backend-neutral; it does not infer semantic importance from backend data: <https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md>.

The same primary llama.cpp server documentation defines `POST /apply-template` as the non-inference operation that converts `/v1/chat/completions`-style messages into the exact string expected by the active model and explicitly documents sending that returned prompt to `/completion`. `GET /props` exposes the active `chat_template` and model path, and the current server also exposes chat input-token endpoints. A local 2026-08-26 probe against the Jetson Qwen2.5 server confirmed that `/apply-template` returns Qwen ChatML framing rather than the Llama-3 markers Swaag previously hardcoded. Swaag therefore keeps role/content prompt construction model-neutral, delegates live llama.cpp serialization to `/apply-template`, hashes the complete model/template identity, and rejects identity changes before generation. Remote OpenAI-compatible providers still need provider-specific capacity and serialization-accounting discovery rather than pretending a local template is authoritative: <https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md> and <https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server.cpp>.

The OpenAI Models API standardizes only basic identity/ownership metadata and does not expose context capacity or a tokenizer endpoint. Swaag therefore cannot infer a context window from an OpenAI-compatible label or model name: <https://developers.openai.com/api/reference/resources/models>. Provider extensions can add stronger facts. OpenRouter documents `context_length` in its model catalog and defines `provider.require_parameters` as an OpenRouter-specific routing field, so Swaag reads the former only from returned metadata and sends the latter only to OpenRouter: <https://openrouter.ai/docs/api/api-reference/models/get-models> and <https://openrouter.ai/docs/guides/routing/provider-selection>. Current vLLM exposes `max_model_len` on each `/v1/models` card and a root `/tokenize` extension that accepts chat messages, returns exact token IDs/count, and reports the deployed maximum model length. Swaag uses those discovered facts when available, but keeps remote serialization marked provider-opaque because vLLM's OpenAI-compatible request does not return the rendered chat-template string: <https://docs.vllm.ai/en/latest/api/vllm/entrypoints/openai/models/serving/> and <https://docs.vllm.ai/en/latest/api/vllm/entrypoints/openai/api_server/>.

OpenTelemetry has GenAI semantic conventions for model, agent, and tool telemetry. Prefer those conventions for operational traces and metrics while keeping telemetry distinct from durable semantic execution history.

Rechecked on 2026-08-28 against the current OpenTelemetry GenAI, HTTP, propagation, W3C Trace Context, and Python guidance:

- GenAI inference spans represent a logical operation, including automatic retries, use `CLIENT` for an out-of-process model server, and require `gen_ai.operation.name` plus `gen_ai.provider.name`. Agent invocation and agent-side tool execution use the current `invoke_agent` and `execute_tool` conventions. These conventions remain Development, so keep the mapping isolated and version-conscious: <https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md> and <https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md>.
- Current metrics include `gen_ai.client.operation.duration`, `gen_ai.client.token.usage`, `gen_ai.invoke_agent.duration`, and `gen_ai.execute_tool.duration`. Token usage must not be invented when it cannot be obtained efficiently; Swaag uses backend counts or its exact tokenizer-backed input count and omits unavailable estimates: <https://github.com/open-telemetry/semantic-conventions-genai/blob/main/model/gen-ai/metrics.yaml>.
- Prompt, message, tool-argument, and tool-result content is sensitive opt-in data. Swaag's default instrumentation emits mechanical identifiers/accounting only, not semantic content. Library instrumentation remains provider-neutral, while the long-running CLI hosting application now installs/configures the Python SDK and batched OTLP/HTTP exporters only when a standard endpoint environment variable is present: <https://opentelemetry.io/docs/languages/python/instrumentation/> and <https://opentelemetry.io/docs/languages/python/exporters/>.
- W3C Trace Context defines lowercase `traceparent` and optional `tracestate` as the interoperable request carrier, requires invalid fields to be discarded, and forbids personally identifiable information in either field. OpenTelemetry's propagator API requires extraction on receive and injection on send. Swaag therefore accepts only those two bounded fields, uses the API package's explicit `TraceContextTextMapPropagator`, extracts them at AG-UI/A2A HTTP and localhost JSON-line adapter boundaries, carries the resulting context across asynchronous worker submission, and injects the active model span into every llama.cpp/OpenAI-compatible backend request. It does not propagate arbitrary baggage or semantic content: <https://www.w3.org/TR/trace-context-2/>, <https://opentelemetry.io/docs/specs/otel/context/api-propagators/>, and <https://opentelemetry.io/docs/languages/python/propagation/>.
- Current stable HTTP span conventions use `SERVER` spans, `http.request.method`, `url.path`, `url.scheme`, low-cardinality `http.route`, `http.response.status_code`, and `http.server.request.duration`. Swaag's fixed protocol routes use those names; the non-HTTP localhost adapter stays under an explicit `swaag.protocol.*` namespace rather than pretending to be HTTP: <https://opentelemetry.io/docs/specs/semconv/http/http-spans/>.

- The current GenAI metrics define client operation duration/token usage and server duration/first-token/per-token timing, but not a stable queue-depth or queue-wait convention. Queue/KV-cache/prefill metrics remain an open proposal. Swaag therefore keeps its admission measurements under the explicit `swaag.inference.*` namespace rather than mislabeling client-side scheduler data as standardized server telemetry: <https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md> and <https://github.com/open-telemetry/semantic-conventions-genai/issues/87>.

- The Python exporter guide recommends sending production telemetry through a Collector and documents OTLP/HTTP as a lossless general transport. The official Collector publishes Linux ARM64 binaries and systemd packages. Release 0.159.0, published 2026-08-18, is checksum-pinned by Swaag's host installer rather than fetched as an unversioned latest artifact. For this local host, a loopback OTLP receiver plus the contrib file exporter provides a backend-independent, inspectable sink without exposing telemetry on LAN/VPN interfaces. The file exporter is still alpha for traces and metrics, so its size/time/back-up-bounded rotating OTLP-JSON files are operational evidence rather than Swaag semantic state. A real service-shutdown probe exposed an upstream nil-writer panic when one file-exporter component was shared by trace and metric pipelines; the host config therefore gives each signal an independent exporter and file. Collector self-metrics are disabled instead of opening an unregistered secondary listener: <https://opentelemetry.io/docs/collector/install/binary/linux/>, <https://github.com/open-telemetry/opentelemetry-collector-releases/releases/tag/v0.159.0>, and <https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.159.0/exporter/fileexporter/README.md>.

When a design task says to research an open question, actually search documentation, specifications, papers, implementations, and the local machine where relevant; compare alternatives; perform safe experiments; and record what passed, failed, and remains uncertain. Do not convert an open research instruction into an unsupported architectural assertion.

Swaag's browser capabilities are availability-gated mechanical tools, not deterministic research routing. Search and page calls expose bounded structured previews, but every call stores the exact raw provider response and diagnostics as integrity-checked artifacts with hashes and canonical tool-result lineage. The LLM decides when research is valuable and when a raw artifact needs targeted re-expansion. A live Jetson smoke test on 2026-08-26 successfully queried DuckDuckGo through the local aubro backend and recovered the exact response through Swaag's artifact store.
