# Foreground single-pass replies and early tool acknowledgements — October 20, 2026

## Requirement and authority

The recording-derived Infra rules require a short, semantically competent user-facing model step with the original finalized user message, trusted compact system state and relevant history. Direct conversation must not require additional orchestration merely to answer. Authorized deeper work should proceed independently while its truthful first reply is read or spoken. A queue receipt is not proof that a tool has executed or that a worker has started. See Infra's `docs/guidlines/agents/fast_user_facing_dispatch_and_preemption.md`, `agents/user_goals_and_answer_first_communication.md`, `gui/voice_interfaces.md` and `gui/core/06_action_acknowledgement_and_progress.md`.

## Implemented, opt-in behavior

Two independent `communication` switches are introduced, both disabled in library defaults:

- `single_pass_direct_replies=true`: when the first compact foreground model action contains a nonempty direct answer, no tools, no new/unresolved questions, no prior effect, no pending user control, no resume and no numeric exact-word-count requirement, the answer is committed without another LLM completion/direct-reply verdict. The history records `verification_scope=foreground_single_pass_unreviewed`, **not** an independent certification. This is a latency/quality policy choice: the initial model still owns the semantic distinction between mere conversation and requested action. An erroneously omitted tool call is not detected by a second reviewer in this path. Noncompact action modes and workers remain unchanged.
- `early_tool_acknowledgement=true`: the initial *validated, accepted* foreground tool action records a speech-stream `assistant_progress` event **before** executing its selected tools, instead of waiting for receipts. Its model-authored message must be a truthful intention, never a claim that a tool succeeded or a worker started. Exact tool results, resumed actions, corrections, independent completion checks and eventual errors continue on the execution thread independent of speech playback. Subsequent tool progress and final result are still available. The first action's old late-progress event is suppressed to avoid a duplicate. The existing durable control fence protects against executing actions selected against superseded user instructions.

The existing runtime has no dedicated small fast communication stage. These changes reuse its *one* capable foreground action model and its already asynchronous conversation-stream executor rather than introducing a second routing authority. The first model action remains affected by actual server prompt processing and decoding speed; there is no sub-second latency claim.

## Reproduction, limits and evidence

The original voice profile uses Coder as foreground and Qwen3.8 Q8 as default worker. A live isolated production-equivalent Coder turn, on its actual server with a fresh SWAAG orchestrator and no prior history, answered its identity question using exactly **one** model request and no tool calls. The result was correctly grounded as SWAAG orchestrator, but took about **22.2 seconds** wall clock; roughly 6,466 input tokens and 54 completion tokens, with first output token at about **13.4 seconds**. The model was co-resident with other Thor inference workloads; the measurement is not a normalized benchmark or an assertion that tool-free speech is now fast enough. A separate stripped-down probe without the canonical orchestrator role also made one model call but answered its identity too generically; do not use that simplified probe as identity acceptance.

A live isolated model-to-tool trial selected `load_tools`, then `calculator`, then generated the final result. Its independent completion evaluation ran normally. The initial acknowledgement was emitted around **30.4 seconds**, the next intermediate message around **53.2 seconds**, and the final response around **90.1 seconds**. It illustrates genuine speech/work overlap, but also establishes that the initial foreground action is too expensive for the desired low latency. The multiple deep model calls are **after** the first acknowledgement. The live trial did not test a physical Android phone or speech playback.

The first focused deterministic suite passed **44 tests**. The complete offline suite for this code with the supported Python 3.13/SQLite runtime passed **1,535 tests**, **3 skipped**, **zero failures** in 315.60 seconds. The dedicated new regressions assert that an eligible direct answer uses exactly one model call; tool work still receives the full completion reviewer; a speech-stream acknowledgement is observable while the tool is deliberately blocked; and a user correction received during model inference prevents stale tool execution or early announcement.

## Remaining work

The foreground prompt in the production-equivalent empty session still costs about 6,466 input tokens; roughly 3,000 to 5,000 token-scale static guidance and schema text plus dynamic worker state contribute. The Qwen Coder server measured around seven generated tokens per second on a separate tiny direct-request probe under current load, not the earlier roughly sixty-five-token-per-second reference. Measure contention, prompt prefill, output decoding, semantic correctness on mixed instructions, as well as actual STT/TTS/phone first-audio latency before declaring the interface fast. Do not enable one-pass completion for workers or evidence-dependent tool results. A dedicated short-response/handoff model operation is a possible next architecture only after an auditable, authority-safe direct-reply commit and no-lost-work handoff have been designed and tested.

Rollback is to disable the two communication switches in Thor's profile, then restart only SWAAG when live work is quiescent; worker model servers are unaffected. The previous code path remains available when both switches are false.

## Separate short-model dispatcher feasibility test (not deployed)

A second **read-only experiment** used the already resident full Qwen3-Coder Q4 endpoint directly, with a roughly 150-token initial chat prompt and a two-field JSON-schema response (`reply`, `needs_deep`). Four representative requests took roughly five to seven seconds each; the correct SWAAG identity answer needed no deeper work. The classifier nevertheless **incorrectly marked an explicit "use the calculator tool" request as `needs_deep=false`**, returning its own computed value without executing the required tool. A standalone translation of quoted instructions was unnecessarily classified as needing deeper work. This disproves semantic reliability for that configuration. The experiment was NOT integrated, installed or enabled; do not promote a naive binary action router just because it is faster. Its reproducible setup and observed outputs are retained under Thor's private `/data/var/swaag-audit/2026-10-20/quick_frontend_feasibility.py` and the command execution evidence.

The existing voice gateway source was also inspected. It accepts committed `assistant_progress` events from SWAAG through its transport adapter and streams TTS as soon as that event is durably saved, in parallel with later model inference. Twenty-five offline voice-transport and committed-speech tests passed. This verifies the producer-to-TTS mechanism in isolation, not end-to-end Android playback. Crucially, it does not make the original twenty-to-thirty-second initial model action fast enough.

The cost of a correctly grounded initial role-answer in the full canonical isolated orchestrator is ~6,466 prompt tokens; the elapsed wall time of ~22.2 seconds includes ~21.7 seconds of model call time, demonstrating that the bulk is not current Python context bookkeeping. A separate minimal direct endpoint probe under the current multi-model Thor load generated about seven output tokens per second. Any further speed optimization needs representative GPU/queue measurements and semantically reliable short-context prompting, not a deterministic intent classifier with observed false negatives.
