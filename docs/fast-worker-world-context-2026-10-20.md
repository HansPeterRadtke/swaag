# Fast voice context: current worker jobs, activity, progress and age

Date: 2026-10-20; Thor. This corrects the fast interface's previous state reduction, which exposed active worker counts and up to four opaque IDs, but **not what those workers were doing**. That behavior contradicted the Infra rules in `docs/guidlines/agents/fast_user_facing_dispatch_and_preemption.md`, `agents/user_goals_and_answer_first_communication.md` and `gui/voice_interfaces.md`.

## Implemented data flow

The existing background world-refresh thread constructs the canonical full orchestrator snapshot, then derives a **separate compact immutable fast state** from it. The fast message path copies that already prepared result, checks the indexed task/world revision and capture freshness (at most three seconds), computes elapsed ages from timestamp arithmetic, and passes the resulting structured JSON alongside the exact current user request and relevant recent conversation. It never scans project files, replays worker journals, starts an LLM selector or reads worker history synchronously just to obtain quick status. A missing, changed or stale snapshot cannot be presented as current.

The compact state includes the complete active-worker count and every active worker's ID, objective excerpt (explicitly marked when shortened), status, finite-versus-continuous completion mode, configured model route, start timestamp and elapsed runtime, last worker-authored task activity and the age of that report, reported next action, observed supervisor inference phase, and explicit progress/ETA evidence. It also includes active plan goals, node states, how many finite plan nodes are complete, node-count-based progress (clearly **not** a worker's percentage), dependencies when cached, recently completed work and pending question counts. Complete worker objectives, model reports, real tool receipts and history remain stored and accessible to the full orchestrator for deeper queries.

The worker's latest status and latest `agent_progress` event are read **independently** from the indexed history during the background refresh, because a new status update must not erase an older explicit step assessment. Explicit, validated step weights yield an assessed **worker percentage** when finite, or a **cycle percentage** if a task is deliberately continuous. No elapsed-time ratio, token count, heartbeat or node count is passed off as worker percentage. A worker's ETA is only included when an explicit model-assessed remaining-time estimate includes declared assumptions. The snapshot provides the estimate's age and indicates when its estimated deadline has passed, rather than claiming a stale estimate is current. If no assessment exists, both percentage and ETA are null/unknown. A continuous task has no overall completion percent or finite ending ETA.

The fresh-state prompt explicitly allows the user-facing Qwen Coder to answer current worker/plan/status questions without delegating them to a second LLM, but it must delegate requests requiring missing source evidence or any actual side effect. Mechanical worker states and model-authored progress remain distinct: a recent heartbeat does not independently prove progress or external success. The voice reply defaults to concise spoken durations. For a large number of active workers, all worker identities/tasks are included rather than silently listing only a small arbitrary subset; the objective excerpt is labeled and full details are accessible through the original canonical orchestrator.

## Test evidence and limitations

The focused deterministic cases exercise multi-day workers, a model-assessed twenty-five-percent worker state, a plan at fifty percent of completed finite nodes, old reports, expired twenty-second remaining-time estimates, intentionally endless jobs with cycle percent only, no explicit percentage/ETA, worker-status question answered with a single model call, correct replay/correction handling, background snapshot precomputation and rejection of snapshots after a changed task revision. An earlier live Coder Q4 synthetic-status trial was correctly able to answer the worker identity, work and runtime directly, but also exposed a model error in which a plan-node percentage was incorrectly described as worker completion. That defect motivated separating the two percentage fields and making the prompt's distinction explicit. A later isolated Coder test with the corrected labels answered all three representative live-status questions directly, keeping missing worker progress/ETA unknown; generated reply latency remained predominantly model decoding, not host orchestration.

The currently active Thor warehouse worker has **no recorded `agent_progress` event** in the inspected session. Its real worker percentage and ETA therefore remain unknown. Any immediate percentage given for it without a new explicit assessment would be fabricated. The ongoing supervisor inference phase, actual start time and latest authored status are independently useful current-state observations; the previous long-running activity alone does not establish that the task is nearly done.

This is a SWAAG source change. It does not replace model weights or the speech gateway. A running Python SWAAG service must be restarted to use it, but active Qwen3.8 worker sessions must not be interrupted merely to activate this faster state view. Keep the existing idle-safe deployment guard and update its pinned SWAAG source revision only after tests and a clean integration commit.
