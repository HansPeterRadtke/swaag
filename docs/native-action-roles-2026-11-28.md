# Action-prompt native role serialization — November 28, 2026

The canonical durable conversation remains ordered `Message` events, with source provenance, full original user content and recoverable tool outputs. This change affects **only the model-facing assembly** for the action and action-tool-call prompt builders. Previous assistant source turns now become actual `assistant` messages in the model request; previous and current user messages remain `user` messages. Ordinary model instructions, retrieved context and quoted tool results remain explicitly bounded `user` content. The system instruction remains the first native `system` message. Source messages and instruction components are still included unmodified in the fallback flat-completion text, so the change is lossless at the component level. Native transport still carries the readable `[USER]`, `[ASSISTANT]`, `[TOOL]` provenance labels; this initial improvement does not reduce their token overhead.

**Not implemented:** provider-native tool call/result objects. The installed JSON-schema action contract returns a structured object with `tool_calls` inside its content rather than Chat Completions `assistant.tool_calls` and provider-issued tool-call IDs. Sending a `tool` role without the matching ID would fabricate protocol state or be rejected. Tool outputs therefore stay quoted and labeled inside `user` messages, not trusted as instructions. Full native tool calling needs a verified backend capability and an explicit stable tool-call-ID mapping in durable source events, followed by separate round-trip and replay tests.

The backend's actual `/apply-template` renderer or compatible chat endpoint must accept multiple alternating user/assistant messages. Existing prompt accounting materializes the *entire* native-message list against the server chat template before admission; per-component hashes, source links and the precise serialized prompt remain available. A plain text completion backend still receives the preexisting flat fallback prompt. Further measured work is required for history relevance, compaction, API-native tool behavior, token reductions, repeated completion loops and a live agent demonstration. A passing pure builder test does not establish improved model intelligence or reduced token cost.

Reproduce the isolated role tests from the project checkout using `.venv/bin/python -m pytest -q tests/test_action_native_roles.py tests/test_tool_result_provenance.py`. On Nitro, broader AgentRuntime-based tests fail at fixture setup because its `.venv` uses SQLite 3.50.4 and the current source requires >=3.51.3; Jetson's `.venv` has SQLite 3.53.1 and is the appropriate existing environment for the complete regression run. The current Python 3.11 source compile succeeds; a separate `/data/venv` Python 3.12 environment lacks `opentelemetry.context` and cannot be counted as a fully configured test environment.

## Repeated byte-identical tool output correction

The November 27 failed Nitro session's recorded final action prompt, event 4647, was 324,713 characters and reported 108,238 prompt tokens. Of the serialized characters, 287,772 were tool-result components. A read-only replay of that saved prompt's component text found twenty-seven large byte-identical repeated result bodies that would be replaced by source-linked references under the new optional deduplication policy: 324,713 to 96,074 characters, a **70.4 percent reduction in visible character count** on that historical *simulated* request. This is not a replayed model call, not the exact earlier Codex comparison request, and **not a measured token or latency improvement**. Each duplicate retains its individual source event sequence and recorded hash. The earliest selected occurrence retains its complete exact body in the initial assembly, while subsequent context compaction may legitimately exclude that earlier body; both original events always remain retrievable from durable history. The reference never promises that the first body survived context selection. Results with fewer than 512 characters, missing integer source-event sequence or distinct bytes are never replaced. These are immutable exact duplicates, not semantic summaries, and the change is limited to action/tool-call prompts, not direct history reads or other semantic operations. Exact hashes and the first occurrence are verified in isolated tests.

Installed Codex CLI on Jetson identifies itself as `codex-cli 0.150.1`. Corresponding source tag `rust-v0.150.1` at `codex-rs/core/src/context_manager/history.rs` uses `for_prompt` to normalize and select native `ResponseItem` messages and tool/function results according to input modalities. That source's `estimate_token_count` explicitly uses approximate, byte-based token estimates rather than a guaranteed tokenizer count. At `codex-rs/core/src/compact.rs`, `sess.clone_history()` supplies the compaction input; `build_compacted_history` preserves selected recent user texts with a 20,000 approximate-token cap plus a summary; `replace_compacted_history` replaces the *prompt history*, not necessarily every underlying persisted source event. In contrast, the recorded SWAAG request carried repeated full tool outputs even when identical. The historical matched diagnostic cited by the owner reports 73,114 SWAAG input tokens versus 16,042 Codex input tokens (about 4.56 times), but exact historical Codex HTTP request bytes are unavailable; no byte-identical cross-agent benchmark is claimed. Further work must inspect exact current Responses request assembly, cached inputs, compaction thresholds and equivalent task-level usage before attributing the entire difference to this defect.

## Completion-evidence bound

The completion evaluator previously had no independent cap on successive requested history-source expansions when the model kept asking for new evidence: `context.max_compaction_rounds` only bounds context-overflow recovery. The source now allows at most three evidence expansion round trips and twelve separately identified sources per request before issuing a durable **incomplete** verdict with a retrieval-budget reason, not a fabricated success or an indefinite review loop. This is a conservative verification limit, not evidence that the request was completed, and it does not destroy or rewrite any historical source. The outer action loop already has a separately configurable maximum number of rejected completion attempts; tests must independently verify both bounds.

## Exact historical comparison request (read-only source audit)

The precise November 27 SWAAG request in the original Nitro session `/data/var/swaag/sessions/session_813a2a3f8510/complete_history.jsonl` is durable event **4484**, with prompt-built event **4481** and corresponding model response event **4554**. Run `python scripts/audit_swaag_model_input.py /data/var/swaag/sessions/session_813a2a3f8510/complete_history.jsonl --request-sequence 4484` (run against the owner-private original, never copy that JSONL into Git). The audit verifies every native role and content range against the exact request fields, then prints **aggregate counts only**. The request had `system` 9,010 characters and `user` 275,455 characters. The returned provider usage was **73,114 prompt tokens**, whereas SWAAG's independent conservative preflight budget was **94,884 input tokens** (29.78% greater than provider-reported usage). The observed model completion took **314.104 seconds**, including **280.508 seconds before the first completion token**, on that old request. This does not isolate model contention, prompt processing or response generation as the cause of its latency.

Its action prompt comprised **284,650 characters**, of which **249,286** were tool-result text. Replaying only the exact duplicate-body replacement against those *saved* prompt components yields **25 duplicate sources**, **190,948 fewer model-visible characters** and **93,702 projected remaining prompt characters** (67.1% fewer characters); this is a **source-trace simulation**, not a new model request, an observed token count or a measured speedup. This distinction is important: the model-reported **73,114** tokens are from the exact old request, while the estimated **94,884** are a different, deliberately conservative budget quantity. The other Codex diagnostic's **16,042** tokens are separately reported, but its exact old HTTP payload is still unavailable. Do not equate the three measurements or attribute all differences to one mechanism.

The script fails closed if `prompt_built` components, roles or native serialized contents do not match the original model request. A synthetic test checks detection of a tampered request, exact duplicate counts, and redaction of source text. Reproducibility requires read access to the private Nitro history, not raw source publication.
