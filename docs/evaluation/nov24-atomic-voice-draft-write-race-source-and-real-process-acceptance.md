# SWAAG: atomic intent-epoch and speech-draft persistence acceptance

**Status, November 24, 2026:** A genuine concurrency defect in the *unreleased* Jetson WebSocket voice-server candidate has now been corrected and verified in isolation, including a forced overlap of a real durable JSON write with newer manual input. The corrected source is **not installed** as a production service, has not accessed the owner's Android microphone, and is not evidence of authenticated speaker identity or an active turn-classification model. All source files, exact private test receipts and test limitations are retained. No real model/agent/third-party provider calls occurred in the new experiments.

## Actual defect and security effect

The preceding release candidate (`cloudflare_ws_voice_server.py`, SHA-256 `e0939fd23aefd11f6d3d8bfd0158508b7b2f0a4f75fb70467e67bced5d06f030`) already corrected a meaningful live source race: a delayed transcription from an old WebSocket could no longer save a stale draft after a new mobile recording began. That preceding change was genuinely tested against four separate source-backed Jetson server processes and contrasted with one preserved original failure. It still did a validity check **before** submitting `record_draft` to an executor thread. Another user intent could theoretically arrive in the interval from that check until durable `fsync` and file replacement. That race was a **hypothesis in the prior handoff**, not a previously observed live defect.

The new patch makes the epoch check and durable speech write a single **per-conversation serialized transaction**. The newest source is derived deterministically from the seven exact previous source modules with only `cloudflare_ws_voice_server.py` changed; its SHA-256 is **`3d4e6e029aa4a467684c618dc31cfd60d53d77939843f547d394b04a979bad2f`**. The other six modules are byte-for-byte the previous release candidate; none of the live systemd units, installed Jetson server code, original audio or owner account configurations were modified.

The patch stores the user-intent epoch under a dedicated `threading.RLock` per conversation. A new voice input or control advances that epoch. An asynchronous speech draft receives an expected epoch captured when its recognition began; it may append or update durable history **only while the shared lock still proves the epoch current**. The lock remains held through the underlying `VoiceCore` per-conversation storage lock, atomic temporary file write, `fsync`, rename and directory synchronization. A newer manual or typed request supersedes older **unsubmitted speech drafts** that were legitimately persisted before the newer request won the lock. Their rows and audio references are retained as `status="superseded"`; no historical audio or other user file is deleted. A stale older worker's second draft write and status-update attempt fail closed. Other conversations have separate locks, so they are not serialized by the affected conversation's disk operation.

This makes the persisted source order explicit: if an old writer already owns the transaction, the new input waits, then retires that old draft before continuing. If the new user input advanced the epoch first, the old writer cannot persist its draft. This is stronger than a generation check outside a background executor, and it remains effective after the newer socket disconnects.

## Measured independent private source and durable storage test

The bounded true-source test `scripts/demos/verify_isolated_voice_atomic_storage_race_once.py` was run **once**, in a separate Jetson Python interpreter with the exact seven-module candidate code and an isolated `VoiceCore`/private configuration. It used the **real** `atomic_write_json` function with private JSON files and actual `fsync`/rename. A controlled thread barrier stopped the older ASR writer *inside* its protected filesystem write after the source epoch check, while a second thread initiated newer manual input for the same conversation. A third operation for an unrelated conversation wrote independently. After releasing the writer and joining both threads, the checker re-opened the actual durable history files.

Measured outcome: **passed**, about **0.44 seconds** for the whole isolated process, including deliberate blocking; an unrelated conversation completed its private write in about **0.01 seconds**. The first conversation contained two rows: the old previously admitted speech row was `superseded`, carrying its original audio **reference**, and the genuinely newer speech row was the single `draft` at the new epoch. The independent second conversation contained its own single draft. A later old-epoch `record_draft` and `update_turn` both returned rejection and did not alter the history. This test writes **placeholder recording-path strings**, not the original real audio; preservation of audio bytes is separately supported by earlier speech/Phonon recordings and was not re-measured in this test. The exact immutable private result SHA-256 is `84e57fa00d0a8da10e0874a3644782517b5ecb411b6b72276955ec3471198182`.

The direct on-disk test alone is not a full voice test. Therefore the *same new source revision* was tested through **four separate actual Jetson WebSocket server processes**, each on an exclusive private localhost port and configuration with all external ASR/LLM/TTS/worker routes disabled. Each received binary PCM corresponding to the prior genuine SWAAG/Phonon output WAV, but a **local fake** ASR relay deliberately held and released exactly one controlled transcript. These tests specifically assessed source acceptance, cancellation, replacement socket handling, speaker-review drafts and the absence of unintended sends; they do **not** measure real Whisper transcription accuracy, actual phone microphone sound, or full audio playback.

## Remaining limits before a production release

The per-conversation mutex can briefly block the live event loop while an earlier background writer finishes a slow filesystem synchronization. This avoids accepting a newer manual recording *ahead of* an old write already admitted to durable persistence, but adds potential latency if disk `fsync` is unusually slow; heavy disk pressure and process crash/power-loss acceptance should be measured separately before promoting this code. This patch also does not establish cross-process epoch fencing for two independently running server processes pointing to the same storage root; the installed service operates as a single process and these tests ran separate processes with separate roots. Avoid using shared storage for multi-process writes without a separate transactional design. The in-memory per-conversation lock/epoch maps grow with distinct conversation IDs and should have an owner-controlled lifecycle plan if many untrusted conversation names are accepted. More exhaustive stress tests are still useful; passing one bounded forced overlap and four real WebSocket flows is not universal concurrency proof.

The existing **live** Jetson voice service remained at its older source SHA-256 `561183f64ae76a9aa92e18b8f2a8c1192b7f9fecc7597233bb363bb64e85415f`, PID `3413413`, and its health is `ready=false` because the separate Thor voice gateway still reports HTTP 503 for the missing dedicated classifier. The approved production pathway is an idle-session check and coordinated **reversible** rollout of the verified speaker-review source together with the necessary dependencies; none of that occurred here. A real Blackview SWAAG Android client is not installed or physically verified. Genuine user mic transcription, voice playback, interrupted network recovery, enrollment and **resistance to replayed or mimicked owner speech** remain outstanding. No unverified speaker should be able to instruct remote tools automatically; the guarded private candidate retains manual review only. New owner-facing Raspi MP3 or daily status report has not been created, because the deliverable is technical groundwork rather than a released product or owner decision.
