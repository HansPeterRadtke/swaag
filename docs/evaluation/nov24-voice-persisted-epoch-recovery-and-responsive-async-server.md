# SWAAG: Recover persisted voice intent revisions and keep other conversations responsive

**November 24, 2026. Current state: reproduced and corrected two additional defects in the already-unreleased, manually guarded Jetson voice-server candidate. Source and test tools are published in SWAAG main; the corrected source is not deployed to the actual owner voice service.** In a new, source-pinned, private real Jetson WebSocket test, the prior candidate failed to retire an older speech draft when the process had restarted and a new manual recording began. The prior candidate also blocked the entire asyncio event loop during a deliberately slow private filesystem operation. A new single-module candidate fixed both without changing the existing per-conversation durable storage transaction or any of the six other source modules. All nine new bounded model-free tests were independently rechecked against original private receipts, logs and histories.

The original, already archived seven-module W69 candidate's server file was SHA-256 `3d4e6e029aa4a467684c618dc31cfd60d53d77939843f547d394b04a979bad2f`. The deterministic W70 patcher, `scripts/demos/prepare_isolated_voice_persisted_epoch_async_guard.py`, will only accept those exact seven module bytes, produce a new private directory and modify **only** `cloudflare_ws_voice_server.py`, which must hash to `f3283c43a196595c4b1fade69e6f2ef0f23943dc6d0b91c5b5ab63f16c17c996`. The unmodified supporting files and private source-manifest SHA-256 `f6372eb49372fde646dbadbc51bdcede078be98008af14d6489542980fbc33bc` remain under the Nitro and Jetson Wave70 scratch roots. Neither the older W69 source nor any original one-use result was changed.

## Real restart problem: a persisted draft had a higher epoch than the new server's memory

The prior cold-restart acceptance test proved an earlier source could **restore** the newest unsubmitted draft on connection and reject a forged speaker-authority commit. It did **not** test what happened when the reconnected user explicitly began a **new** manual recording. The process-global `CONVERSATION_INTENT_EPOCH` dictionary was initialized empty on restart; the first new intent advanced a missing counter to `1`, even though the actual saved history already held speech epochs `1` and `2`. The retire-old-draft predicate only retired rows with an epoch less than the new counter. As a result, the stored epoch-two speech draft stayed active despite a fresh manual-recording command.

We proved this with an actual, separately launched Jetson WebSocket server process against a private **copy** of the W69 durable source history. The original saved file, SHA-256 `bdde160a4996a1f38e8a88366bf2bb63e6ad3a65b2ebd26687326a03158102fc`, contains two rows: `superseded` at epoch one and `draft` at epoch two. The original W69 candidate's one new `begin_manual_utterance` control request returned a persisted status list of **`[superseded, draft]`**. That is a new genuine source-observed failure, *not* a replay or revision of the previous W69 success case. The complete immutable original new-test receipt is SHA-256 `76b020c9a008f6b2d98bd31ccf32826fca80cb836f52cd135b6a2032558cc5a2`.

The corrected source initializes each in-memory conversation revision from the **maximum valid revision recorded in that conversation's durable history**, including `asr_intent_epoch` and `superseded_by_intent_epoch`, under the existing per-conversation storage mutex. It rejects malformed, negative, boolean and unreasonable revision metadata rather than accepting unpredictable counters. On a fresh run with the same immutable original private history, the newest new-input epoch advanced beyond the persisted epoch two, and the previously active draft was marked `superseded`. The persisted status list became **`[superseded, superseded]`**; no speech text was submitted, no old audio was removed, and no tool or model was contacted. This was a second, separate actual Jetson WebSocket source process with receipt SHA-256 `067b704ef334bd980909ab2db170e126364e83f9b5e2278e8b5030fd337080f2`. The true original W69 source still fails in the new scenario; the corrected W70 source succeeds.

The patch also handles older speech rows with **no revision metadata at all**. A distinctly new source-backed on-wire test constructed a transparent legacy-format **derived fixture** by copying the hash-verified original W69 saved history into a separate private conversation and setting its speech revision fields to `None`. This is a **derived test fixture**, not an original user conversation or an independently observed historical migration. When the corrected source received a new manual recording after cold start, it retired the old unsubmitted speech draft without loss of the recorded row. That new genuine one-use Jetson server result is SHA-256 `a3a9b9d9226485b119eca018051caa708cce48d9f1eccda99fe64985a1c607c9`. Ordinary **idle** reconnect still restores a legitimate pending speech draft, as separately checked below; epochless retirement is only triggered by explicit new user input.

## Responsiveness: retain storage atomicity without blocking the event loop

The source already guarded the draft's compare-and-write under a per-conversation `threading.RLock` and `VoiceCore.conversation_lock`, including real atomic temporary JSON write, `fsync`, rename and directory sync. However, `VoiceSession.cancel_response` and five other asynchronous handlers directly called that **synchronous** epoch-advancement function on the asyncio event loop. When storage or another thread was busy, the function could delay heartbeats and unrelated user conversations. This was a source-identified possible degradation, then directly reproduced.

To compare the same operation fairly, two **different, new** source-pinned private interpreter runs each loaded a copy of the actual W69 stored two-row history, seeded the same current epoch, and called the actual `VoiceSession.cancel_response('new_manual_utterance')` method. Each injected a **controlled 0.70-second test-only sleep before a real atomic JSON write** to model unusually slow durable storage. Each had an independent 12-millisecond asyncio heartbeat task. The old source run measured a largest heartbeat gap of **0.718 seconds**, one real durable JSON write and **33** heartbeat samples. The corrected source run measured a largest gap of **0.016 seconds**, the same one real durable write and **89** samples. Its new manual intent itself took approximately **0.713 seconds** to complete; the old intent also took approximately **0.709 seconds**. The improvement is responsiveness for other queued event-loop work, **not** a claim that the durable user input magically becomes fast. Test receipts: old SHA-256 `3ebf9463466667b0370085882a520be335f25d604e1b41bfb2052870bd9c32d7`, corrected SHA-256 `c3c5f9c8f7d59c6ae09d96149ebfeff6b1f7905e2b867526f8190359a9b966e0`. The roughly **45-fold smaller** observed heartbeat gap applies only to this bounded injected delay, not to arbitrary future hardware/network conditions.

The source correction moves **six** direct calls that advance the conversation epoch into the existing `run_blocking` executor helper. It preserves the in-executor per-conversation lock and atomic draft commit, so a newer user request cannot interleave its committed revision inside an earlier already-admitted durable storage transaction. As a separate safety/property check, the source returns a well-defined failure for invalid stored revision metadata and refuses a revision above the checked limit. An event loop request may still need to **await** a busy transaction; the event loop remains free to process unrelated messages while it does.

## Reproducibility, publication and limits

Versioned source instruments are `scripts/demos/prepare_isolated_voice_persisted_epoch_async_guard.py` (deterministic single-module patch), `scripts/demos/verify_isolated_voice_persisted_epoch_on_new_manual_once.py` (prior failure and new source real cold manual input), `scripts/demos/verify_isolated_voice_nonblocking_intent_fsync_once.py` (actual handler with injected slow storage), `scripts/demos/verify_isolated_voice_async_epoch_ws_once.py` (four separate PCM/WebSocket cases), `scripts/demos/verify_isolated_voice_legacy_epochless_restart_once.py` (distinct derived legacy-format case), and `scripts/demos/verify_isolated_voice_persisted_epoch_async_evidence.py` (independent output verifier). Unit tests verify exact source transformations, signed evidence rejection, unique destination, speaker-review config and no-effect preflight. All real source voice/audio and executable one-use manifests remain in **private** Jetson/Nitro Wave70 directories; source code and source-only documentation are published to SWAAG canonical main only. Never repeat the original completed one-use model or voice/provider effects merely to regenerate a result.

The first two cold-restart-run scripts were executed on Jetson from original private source bytes at SHA-256 `ae85ef05da42c941aa7f1fffa55dacbfdcb92c5e0762ffb1295ee81f8fad5d76` and the legacy helper at `3c7954a5b8dd71fcf518a75376d45ec60f4b58cfdf3903a7f36876328b0972b4`. Their Git-published helpers were subsequently adjusted **only** to import the ordinary `re` library at module scope, allowing pure no-network import tests without needing to run the scripts as `__main__`. The real Jetson trials were **not replayed** after this import-only change, and the original exactly executed scripts remain available privately. This distinction is recorded rather than claiming the later helper revision executed that particular experiment.

**What remains unproven:** The candidate has not been deployed, and these tests do not establish full authenticated human voice control, actual Blackview microphone/capture/playback/reconnect, streaming Whisper ASR quality or end-to-end spoken response latency. The **live** Jetson `jetson-voice-ws.service` still runs older source SHA-256 `561183f64ae76a9aa92e18b8f2a8c1192b7f9fecc7597233bb363bb64e85415f` (last checked PID `3413413`); readiness is false because the separate Thor voice gateway still reports HTTP 503 for its missing dedicated turn classifier. The prior broker-denied four-billion-parameter Qwen test has not been retried or bypassed. Existing shared model services and all other workers' active files must remain intact. A per-conversation in-memory lock is not cross-process transactional storage and does not automatically secure multiple server processes sharing a directory; durable revision recovery is tested for one process restart with the current JSON schema only. The current epoch map grows with conversation IDs; an eventual cleanup/expiry design needs testing. And multiple simultaneous clients within one conversation may still merit explicit arrival-order tests even though the protected write is now off the event loop.

The next release decision is a coordinated, reversible, **manual-review-only** Jetson server candidate rollout after real classifier health, idle-connection checks, rollback and physical Android acceptance. No automatic speech-to-tool control from unverified speakers is authorized by these source tests. Owner-facing generic test logs and narration are not created for this intermediate technical milestone; the full evidence belongs in the shared Raspi project exchange and the private checkpoint.
