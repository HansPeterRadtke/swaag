# SWAAG core: structural completion consistency and exact Python source evidence

**Scope:** Core agent only, November 28, 2026. No voice, Android, speech processing, website deployment, provider publication, account change, or existing user task replay.

## Reproduced original failure

The original source-pinned, broker-admitted one-use SWAAG demonstration from the preceding instruction was a *real* local model run: seven completed model requests, five permitted real tool calls, and a demonstrated missing-file failure followed by model-selected listing and two exact source reads. The original frozen Python AST oracle counted five and one top-level test declarations, but the model selected `calculator("4 + 1")`, obtaining the mathematically correct result five for the **wrong input**. The model's final answer was therefore unsupported. The original independent verifier returned `failed_or_unverified` with fourteen of sixteen checks passing. The original 504-event SHA-linked journal, output and independent verdict remain immutable in owner-private Nitro evidence.

A second, independently observable controller error occurred *after* the wrong result. The recorded completion model response at source event 500 claimed `complete=true` but returned the nonempty array `remaining_work=["No remaining work"]`, violating the evaluator's explicit contract: a verified complete result requires `remaining_work=[]`. The controller silently accepted that contradictory model output and recorded its own `completion_evaluated.complete=true` at event 501. `scripts/demos/audit_completion_consistency.py` reads any complete hash-linked journal and reports **only source event numbers, exact provenance checks and contradiction counts**, never user message content. Against the preserved original it reports one contradictory complete verdict and one erroneous accepted-success event, with zero model calls and zero tool effects. Its source file is deliberately read-only and does not alter or replay the original run.

## General contract repair

The action completion validator now treats `complete=true` plus **any nonempty `remaining_work` array** as an inconsistent, unverified verdict, regardless of wording such as “No remaining work” or an empty string. It records a durable `completion_evaluated` event with `complete=false`, preserves the model's exact original `reason` and `remaining_work` in separately labeled audit fields and supplies one actionable instruction to reassess *actual* user and tool/source evidence. It does **not** silently convert the model's string into an empty array, accept the task, or claim correctness based on phrase matching. Existing capped completion rejections still apply; repeat contradictions result in a truthful incomplete turn. A valid complete verdict with an **empty** array and minimal one-responsibility verdicts still follow their previous semantics. This is a mechanical protocol validation rule, **not** a general semantic completion oracle. A model that incorrectly returns `complete=true, remaining_work=[]` could still be wrong and must be caught through independent task evidence and real acceptance.

## Reusable, non-executing source-inspection tool

A new read-only `python_source_structure` tool is registered in the canonical repository and exposed through normal tool discovery. It takes a single authorized workspace path, uses the existing permission-checked file reader, computes a SHA-256 of the unchanged source and calls Python's `ast.parse` **without executing source statements, imports or other code**. Its output includes the exact top-level functions, which are asynchronous, classes, source lines, total functions and `test_`-prefixed function declarations. Nested class methods and nested local functions are excluded from top-level counts. There is no path-based guess about whether a file should be treated as Python: its contents are parsed, and syntax errors fail explicitly. Read-root boundaries, side-effect and stateful tool gates, source size bounds, output schema and original source event audit requirements remain enforced; failures cannot produce partial-success counts. Tool outputs include source hashes and exact event provenance, not model-invented numbers.

This tool is a **capability** that the model must select when useful; Python does not keyword-route user instructions or mechanically decide which tasks are complete. The independently retained failed demonstration's original source files were inspected with this tool after the original task had already ended. Actual source hashes matched the frozen originals, giving five and one declarations, and the real calculator returned six. This is correct source-backed **tool testing**, not another completed model-run demonstration and not permission to relabel the old failure.

## Verification and limitations

The focused tests `tests/test_completion_verdict_consistency.py` and `tests/test_python_source_structure.py` exercise contradictory model output, model-history preservation, bounded retries, consistent verdicts, source syntax handling, asynchronous/top-level declaration counts, no-execute behavior, read-root and symlink escapes, oversized sources, output metadata, side-effect policy and holdout files with varying counts. Test outcomes are recorded in the private project receipt; passing deterministic tests does not establish new live model reliability. All original model/task records and immutable reference hashes remain outside Git.

A genuinely new, distinct broker-admitted model task and independent oracle are required to measure whether the model actually chooses the new structural source tool, reports supported results, and whether the stronger completion guard reliably prevents false positives under more than one outcome. The source-only repair still does not implement provider-native `tool_calls` and `tool_call_id` correlation; existing JSON-action tools remain durable, structured internal tool actions with provenance but are not yet provider-native tool messages. The installed Nitro package and SQLite runtime also require careful separate reconciliation.

## Subsequent separate live verification of the fail-closed controller

The next distinct private source-analysis task used the new structural tool on a **different** frozen pair of actual source files. It demonstrated real model-selected missing-path error recovery, exact top-level AST test counts of eight and seven and a genuine calculator result of fifteen, but the completion evaluator again produced `complete=true` with a nonempty `remaining_work` array **twice**. The corrected controller refused both contradictory claims and bounded the turn as incomplete instead of reproducing the older false-success defect. The separate original-source/hash-backed oracle rejected full task acceptance (twelve of fourteen checks) because the incomplete final response and evaluator did not meet the requested full task. No original history was overwritten or replayed as a new model action.

The subsequent generic prompt-template revision reinforces that `complete=true` requires literally `remaining_work=[]`, never a status string or cosmetic removal after rejection, and that source-backed operands must actually agree with tool results. Unit tests confirm this versioned instruction appears in the exact completion prompt. This is a source-only improvement until independently tested with a new, distinct, authorized live model task. Future work must still prevent **semantically** false `complete=true, remaining_work=[]` claims; the structural guard can prove only that the output contract is internally consistent, not that the external task is genuinely complete.

## Why prompt clarification is not the whole completion fix

SWAAG's deliberately portable JSON-schema subset supports closed objects, enums, arrays and nested `anyOf`, but does **not** support `if`/`then`, `maxItems`, `const` or a root `anyOf`; inspect `src/swaag/schema_portability.py`. Thus the existing root completion schema cannot express “`complete=true` if and only if `remaining_work=[]`” as a direct provider grammar constraint without changing the wire contract and testing every supported backend. The current generic controller invariant rejects the contradictory form with source-linked evidence and bounded retries, while the compact system-prompt reminder attempts to prevent the format error during decoding. It is not independent proof of task success or a guaranteed correction for all models. A future backend-specific wire-contract redesign requires actual provider compatibility, durable replay, and benchmark evidence before promotion.
