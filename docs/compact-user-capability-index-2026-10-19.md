# Compact foreground capability index — October 19, 2026

The Infra agent guidelines explicitly require a short stable SWAAG system description, current worker/plan/global state, applicable user goals and the actual user utterance. They do **not** require full descriptions and schema of every potentially available tool in the user-facing prompt. SWAAG already implements staged schema discovery, so this source change affects only the human/model-readable one-line **capability index** used during fast foreground actions; the selected tool's exact schema and guidance still load on demand. No capability, access authorization, user message, durable instruction or full history is deleted.

This change replaces lengthy descriptions with specific short, verified descriptions for the common foreground capabilities (orchestration control, worker control/status, question revision, notes/lessons, filesystem inspection, calculation, and progress). All actual configured names are still included. Unrecognized provider-specific names keep their configured full descriptions rather than being silently dropped or guessed. The longer exact tool schema is unchanged and remains authoritative when a model selects that capability. The index is not a hardcoded language/keyword intent classifier and does not select tools on behalf of the LLM.

A measured loaded foreground catalog contains **23 available capabilities**. The previous compact index was **2,314 characters**; the new one is **1,527 characters**, a **34-percent reduction in raw index characters** with the same names. The full tool-descriptions and schema text were never loaded for unselected tools in this staged mode. The expected token improvement is less than the character ratio because tokenization varies; calculate actual tokens in the real model prompt. This single optimization does not fix the larger permanent system/durable instruction text or the several model calls used for detailed orchestration and independent completion verification.

An actual isolated Coder-to-Qwen3.8 Q8 orchestration trial passed using this modified index: Coder chose the required orchestration tool via staged discovery, committed a real worker-start receipt, truthfully acknowledged a queued worker and the background Q8 model completed the exact marker task. The foreground answer took **48.4 seconds**; total elapsed through Q8 worker completion was **93.957 seconds** (`/data/var/swaag-benchmarks/compact-index-live-20261019`). These measurements demonstrate unchanged semantics on one task, **not a guaranteed speedup** compared with previous separate trials. The new regression file asserts that all configured tool names remain discoverable, the index contains no tool schemas or full usage guidance, and the user-facing description stays shorter than the full one.

Do not promote this change solely on the narrow successful live test. It requires full offline regression, installed-source compatibility and safe service switching when production operations are idle; neither backend is to be restarted for a prompt-text change. The user's ideal near-subsecond conversational response remains an unfulfilled separate two-stage architecture requirement.

## Resident llama.cpp KV-prefix reuse: verified optimization and current limitation

A separate read-only direct inference probe on Thor's **existing Coder** llama.cpp server used two changing user messages with the same approximately 4,021-token trusted system prefix and `cache_prompt=true`, without modifying either resident model service. The cold request took **3.979 seconds to first text** and reported **3 cached input tokens**. The next two requests took **0.117 and 0.113 seconds to first text**, reporting **4,014 cached tokens** each. Thus this exact installed model/server implements useful prompt-prefix caching; large stable prompts need not always be fully re-prefilled. Source: `/data/var/swaag-benchmarks/coder-interaction-benchmark-20261019/cache_prefix_probe.json`.

The SWAAG transport previously omitted `cache_prompt` for its streaming `/v1/chat/completions` calls. The new request builder enables this *backend KV-prefix option* by default only for explicitly configured `llama.cpp`/`llama_cpp` OpenAI-chat transport and respects explicit caller `cache_prompt=false`. It does not change model choices, tool authority, completion content, response schema, selected prompt evidence, or SWAAG's distinct durable record/replay cassette. Native llama.cpp completion requests and unrelated OpenAI-compatible providers do not receive the option. New deterministic tests verify exact request-content preservation, opt-out, provider isolation and streaming completion compatibility. The amended source passed **1,529 offline tests, 3 skipped, 0 failures** in **295.16 seconds**. Log: `/data/tmp/swaag-kv-index-final-full19.log`.

**Important negative real-system evidence:** in a fresh *two-turn same-session SWAAG* isolated model run using the enabled transport option, the first Coder action requested **4,493 input tokens** and reported only **3 cache hits**; its first token took **5.598 seconds**. After that turn's separate independent completion-check model calls, the second Coder action with a byte-identical **8,236-character system prefix** requested **4,537 tokens**, reported only **5 cached tokens**, and its first token still took **5.572 seconds**. Intermediate completion-evaluation calls replaced the prompt occupying the server's only current context slot (`--parallel 1`). In particular, one middle completion call reused 2,279 cached tokens of an earlier *checker* prompt, not the longer action prefix. Thus enabling KV caching alone does **not** provide the potential 0.1-second first text on the actual multi-call SWAAG path; claiming otherwise would be false. Source: `/data/var/swaag-benchmarks/kv-foreground-turns-20261019/` and its append-only model history. This was in isolated test sessions, not the production user conversation.

The resident Coder server is configured with `--parallel 1`, 262,144 maximum context tokens and Q8 KV memory, while Qwen3.8 Q8 occupies another memory-hungry model service on the same Thor GPU. Adding a second 262K slot or restarting/reconfiguring either model simply to reserve separate action/checker prefixes requires a measured unified-memory admission and user-service concurrency test. **Do not restart the models or increase their KV allocation based only on the direct cache microbenchmark.** To realize a fast foreground reply, the remaining architectural task is to minimize or defer unnecessary semantic calls while retaining model-independent verification for actual external effects, and benchmark prefill/timing with the true prompt, data, model action and safety/authority tests.
