## Correct test surface versus misleading developer-path results

The generic benchmark runner's `AgentRuntime.run_turn_in_session` directly exercises an agent developer session, not the canonical human interface. In earlier isolated real-Coder checks it failed both simple identity cases, answered without SWAAG identity, and made two model calls per question. For the six new conversational developer-path cases, two passed (history pronoun and corrected folder); two identity cases were unsupported and two tool-attempts violated the explicitly zero-tool benchmark contract. These are valid development-path failures, but they do not demonstrate that the deployed voice conversation route has the same defect. Preserve the negative evidence in `/data/var/swaag-benchmarks/conversation-20261103/live/`.

The NEW `swaag.benchmark conversation-acceptance` subcommand invokes the REAL `CommunicationService.orchestrator_message` as used by finalized voice and chat input, with real Coder inference. Each independent case owns a separate private session root and workspace, seeded with actual durable user/assistant messages. There are no shared production sessions, configured tools, worker rights or permitted writes. The CLI preserves durable operation IDs, captures the exact observed final message and independent answer/regex oracle, asserts zero tools/workers, and writes per-case receipts under `/data/var`. The result file and session history are **not** inside the benchmark workspace; an early test discovered the resulting false-positive workspace-mutation verdict and was fixed without weakening the unchanged-workspace assertion.

On Thor, the actual deployed configuration with only development-case session and tool boundaries overridden passed **six of six canonical conversational cases** in the preserved `canonical-benchmark-v2` run. The cases cover identity including rude speech wording, explanatory follow-up from prior actual conversation, pronoun resolution selecting the correct host, latest user correction overriding prior assistant advice, and truthful denial of a previously unexecuted backup. Five fast cases took about 0.7 to 1.3 seconds with one foreground model call. The longer voice-interface explanation took approximately 17 seconds and escalated to a deep action plus completion evaluation. That fallback is slow for a short history-grounded question and warrants a targeted latency/context audit, not an unverified success claim. These six original development cases are not a representative semantic reliability rate, multi-turn scalability study, or untouched final holdout. The October 25 real multi-source false completion remains unresolved.

Focused new benchmark tests passed **33 tests**. Existing broader deterministic regression with the compatible Thor runtime passed **1,731 with three skips**, before the final standalone conversation acceptance module was added; rerun the entire suite after integration when planning deployment. Maintain actual PYTHONPATH `/data/src/github/swaag/src` in testing: the installed site-package is older and can produce an unrelated false failure.

## November 3–4 night continuation: real regression findings and non-deployed fixes

The canonical acceptance catalog first expanded to **seventeen** independent spoken/text conversational cases, up from six. The new cases include German identity, absent private facts, correcting an unsupported prior assistant claim, a possibly sent message with no receipt, forty-two seeded earlier user/assistant history messages containing a displaced fact, late user authority over an assistant suggestion, quoted destructive instructions without tool authority, short pronoun references after genuine recent context, and a conversational codename correction that is NOT an external filesystem update. Every case uses an isolated workspace and independently verifies exact persisted chronological messages, completed durable operation ID, duplicate-idempotency receipt without a second history mutation, absence of tool/worker side effects, and unchanged workspace. A new behavioral oracle additionally rejects unnecessary blocking clarification even if the generated text contains the expected noun. A narrow, intentionally isolated case checking exact earlier test-status wording finished successfully, while a vague short contextual prompt without an explicit history qualifier remains a known unreliable case.

A preliminary fifteen-case Coder run before the completion/schema changes found twelve fully passing. Three important negative results must remain visible: one short source-status explanation called unexpected tools and cost about 322 seconds; one simple follow-up produced an invalid-output loop for about 126 seconds; and one benign quoted-deletion question was originally falsely failed because the oracle demanded a lexical `delet` rather than evidence of no actual filesystem effect. The quotation-oracle defect was corrected, but fixing a test does not prove the underlying model always resolves the reference. A test-process-only deictic prompt comparison recovered the recording-upload topic but still asked an unnecessary clarification, so it was **not deployed as a supposed fix**.

The deployed action schema used to let the model emit `criticality=blocking` together with a nonempty provisional assumption even though the independent semantic validator forbids this combination, resulting in repeated rejected action calls. The now revised **portable constrained schema** branches into a blocking question with mandatory empty assumption and a separate optional-question branch. The action semantic validator still checks optional-question assumption nonemptiness because portable schema intentionally lacks `minLength`. The revised grammar was tested with the real Coder chat-completions endpoint, emitting a valid single blocking question; schema tests also cover old contract compatibility. The exact old user-facing prompt text is unchanged apart from adding a limited completion-evaluator clarification about in-chat fact revisions.

A genuine two-process durable conversation-restart experiment failed initially because the completion evaluator misinterpreted `Correction: replace the project codename Rook with Cedar` as a demand to edit a file and repeatedly rejected its own conversational acknowledgement before an unrelated backend timeout. Its isolated operation remained `outcome_unknown` and was NOT retried. The completion-evaluator system prompt now explicitly distinguishes changes confined to facts stated in the ongoing conversation from real external operations and mandates actual observed receipts for the latter. A fresh two-process rerun then recovered the original durable receipt without modifying history, accepted the correction, and replied `Cedar` from the restored conversation without tools or workers. The reusable source module `swaag.benchmark.conversation_restart_acceptance` provides explicit `--phase first` and `--phase second` commands, using a caller-provided unique private `--output` root and `--config`; it refuses to replay already attempted uncertain second-phase operations. Only accept first/second output after distinct process runs and the second receipt has actually been verified.

The earlier full test pass under the new longer completion prompt found a context-budget-sensitive expectation in `test_reexpanded_completion_evidence_projects_only_after_overflow`: it used an artificially tiny 900-token context window and assumed the independently projected evidence should remain unprojected. With the longer correctly scoped completion system prompt, even exact excerpt references crossed that tiny limit. Reassessing the actual context budget at 1,400 tokens restored its intended exact-search and non-projection check. This is a change to the synthetic benchmark window, not relaxed source-hash or provenance checking. The initial full-suite test reported one failure and 1,737 passes with three skips; the corrected all-tests run must be evaluated separately before claiming a completely green suite.

Real ASR tests additionally covered forty official English LibriSpeech validation/development clips with all forty HTTP calls successful, aggregate WER about 5.7% / 4.1%, and an eight-clip independent German FLEURS validation subset with 160 reference words and WER 1.25%. The FLEURS dataset viewer supplies float-WAV files; direct upload into the resident PCM16-only API correctly failed, so the isolated evaluation converts and hashes the derived 16 kHz mono PCM16 bytes and keeps the original float WAV checksums. Invalid format, wrong sample rate, stereo input and truncated WAV were all rejected with HTTP 400; a genuine two-second silent recording returned zero recognized words. These are small read-aloud slices and not spontaneous speech, loud environments, tail latency, German dialects or full-duplex turn-taking acceptance.

A real authenticated Jetson WSS -> Thor SWAAG -> Nitro LuxTTS -> Jetson PCM round trip for the harmless question "Who are you?" finished with roughly 12.3 seconds to draft, 13.2 seconds to first audio, and 25.5 seconds to final media. The fourteen-second machine-heavy answer was poorly recovered when the exact saved WAV was independently re-transcribed by resident Whisper, proving that protocol success does not by itself establish intelligibility. Three isolated versions of a much shorter identity sentence synthesized in about one second, produced around 2.4 seconds of speech, and were recognized as "I am Swag, your local voice assistant." Actual waveform hashes and source text remain private under /data/var. This is not an Android playback check.

A compact identity prompt now distinguishes the default one-sentence English/German conversational identity from an explicit underlying-model question. The fast prompt remains under its original 2,100-character regression limit and preserves fact-versus-action, recent history, safe evidence, microphone uncertainty and task delegation. The installed foreground-role template retains its original first two sentences; an earlier prepended draft broke two independent direct-reply grounding tests and was corrected.

An eighteenth canonical benchmark case found a separate real bug. The fast Coder correctly generated "I am running the model qwen3-coder-30b-a3b-instruct-q4-k-m", but a broad unperformed-action regex interpreted "I am running" as an unfinished operation and delegated it. The deep controller then gave the wrong Qwen3.8 default-worker model identity after a lengthy verification loop. The safety guard now allows only an exact, entire statement of the actual configured foreground model, in either natural word order, responding to an explicit model question. Other model identities and genuine statements about running tests or work remain delegated. This was verified with targeted model-response fixtures and an independent new real-Coder benchmark: four English, rude, German and explicit-model cases passed in about 0.5 to 1.0 seconds each. No production Python service restart or deployment was performed.

A read-only direct-Coder comparison using a recent real WSS prompt showed 1,846 prompt tokens for full earlier state/history and 626 in a compact counterfactual. Two idle completions per variant took approximately 1.29 and 2.75 seconds full, versus 0.76 and 0.84 seconds compact. Those numbers are confounded by output length, remote scheduler contention and warm caches; trimming current trusted worker state is NOT authorized by this isolated finding. The genuine WSS model response took over ten seconds on a one-slot model, illustrating real contention.

The turn classifier is still absent from its configured Thor localhost 14920 endpoint; gateway health remains HTTP 503 and Jetson overall voice readiness false. Isolated use of Coder as the turn classifier passed 17 of 17 simple English/German text-boundary checks when idle (median ~0.3 seconds), but timed out after eight seconds under model contention. ## November 4 follow-through: deep fallback and original classifier model feasibility

The earlier false background-model identity was not merely a wording defect in the fast response. An isolated run with the fast answer path forcibly bypassed still selected the default-worker Qwen3.8 model name from an otherwise accurate runtime snapshot. A test-process-only added snapshot annotation explicitly identifying the current user-facing foreground model fixed this forced-deep case. The canonical runtime snapshot now carries the independently configured current-response identity next to foreground and default-worker routes, clearly labeled as configuration rather than proof of the actual model weight binary. The actual patched-source deep fallback reproduced the correct Qwen3-Coder identity with no tools/workers. It took roughly 43 seconds, however; fast-path semantics and backend scheduling remain performance priorities. The targeted snapshot/communication tests passed with the new field.

The precise missing Qwen3-VL 8B model weights were located in Thor's original HuggingFace cache: the approximately 5.0-GiB Q4_K_M GGUF and its 0.75-GiB Q8 multimodal projection file. This is not a missing-download problem. Its configured voice classifier port 14920 had no listener or systemd service, despite production gateway requiring it. The central read-only GPU-first resource-broker preflight indicated an eight-GiB request could fit at the sample but admission still required a real atomic reservation and preservation of the four-GiB safety reserve. A **ten-minute logical eight-GiB RAM lease** was granted by the central Raspberry Pi resource broker for this specific isolated test, with no model eviction or external process disruption.

An independently launched **CPU-only** copy of the real Qwen3-VL 8B Q4 model at localhost port 14921 loaded successfully in about six seconds, with a four-thousand-token context and one inference slot. The actual deployed gateway turn-completion classifier was then pointed at this isolated temporary endpoint in a separate test process, never the production 14920 address. The first four English utterance classifications all exceeded the mandated eight-second deadline and were rejected as classifier_invalid; the first outstanding model task also prevented prompt slot-health responses. This approach is **not** an acceptable real-time fallback. We terminated only our disposable test client and new test server (port 14921 closed), verified both existing Coder and Qwen3.8 server health still OK, and independently released the exact central broker lease. No production service was restarted, no active model was unloaded, and no original classifier weights were modified. A GPU-accelerated dedicated service still needs its own safe broker admission, resource scheduling, measured latency, and semantic pause/correction tests before any production installation or readiness claim.

## November 4: recovered GPU classifier feasibility and fail-closed oracle

After the CPU-only model proved unable to answer within the eight-second classification deadline, a second isolated, broker-reserved **GPU** test used the identical original Qwen3-VL 8B Instruct Q4_K_M GGUF already present in the Thor HuggingFace cache. The owner-guideline resource broker initially reported a fitting eight-GiB GPU allocation under Thor's unified-memory safety reserve. A six-minute atomic logical broker reservation was granted, and a transient systemd service with an **eight-GiB memory limit, six-CPU quota, and three-minute absolute runtime maximum** launched the test model on loopback port 14921. Neither the production classifier port 14920 nor active Qwen Coder/Q8 workers were changed. The isolated GPU model loaded in about two seconds, responding to health and inference at the temporary port.

The **actual deployed gateway classifier functions** were exercised against that isolated GPU endpoint, using the original voice prompt and strict JSON schema. Seventeen of seventeen selected English/German end-of-turn utterance cases passed: complete questions, profanity, hesitation, explicit correction, unfinished clauses and mixed German corrections. Observed latencies were generally 0.43–0.51 seconds on the loaded model. For interruption-versus-backchannel decisions, nine of ten initial cases passed, with standalone acknowledgement 'right' incorrectly taking the floor. A more explicit prompt was evaluated *without changing deployed source* on eight extra examples; six passed, while 'right' and 'correct' still triggered wrong take-floor decisions. This is a real semantic false-positive concern. The test corpus is small synthetic text, not actual interrupted noisy microphone audio; do not claim production-ready full-duplex quality from these scores.

The temporary GPU service was explicitly stopped and the exact central broker reservation released. Verified afterward: listener 14921 closed; production Coder/Q8 /health stayed OK; no active model was restarted, and gateway port 14920 remains unavailable. The test was **resource-feasible but did not authorize a permanent new GPU consumer**. Permanent classifier admission requires managed GPU capacity, coexistence with other owners, tested backchannel semantics, and latency/false-positive measurement under concurrency before enabling automatic speech-turn submission.

A reusable, explicit opt-in benchmark module was added at `src/swaag/benchmark/voice_classifier_acceptance.py`. It loads the original canonical voice gateway implementation from a user-selected source tree and verifies that both imported source files match that exact tree, storing source SHA-256 hashes. Its bundled package fixture at `src/swaag/benchmark/fixtures/voice_classifier_oracle_20261104.json` contains thirty-five source-labelled short utterance cases: seventeen end-turn, ten interruption, eight additional acknowledgement/context distinctions. The CLI accepts a loopback-only **isolated** model endpoint but refuses the deployed classifier and gateway ports. It creates the exclusive private result receipt *before* the first model request, so an interruption cannot silently cause a replay, and it changes no production configuration. Most importantly, `kind=classifier_invalid` with a boolean `complete=false` is explicitly a **failed classification**, not a successful negative oracle match. This closes a false-positive weakness in the early ad-hoc classification scorer. Four source-level regression tests passed. A fail-closed acceptance test against the intentionally closed temporary port correctly scored zero of seventeen, never concealing refused connections as correct incomplete utterances. The earlier real Qwen3-VL GPU observations remain in private timestamped acceptance records rather than copied into source code fixtures.
