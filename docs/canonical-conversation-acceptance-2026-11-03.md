## Correct test surface versus misleading developer-path results

The generic benchmark runner's `AgentRuntime.run_turn_in_session` directly exercises an agent developer session, not the canonical human interface. In earlier isolated real-Coder checks it failed both simple identity cases, answered without SWAAG identity, and made two model calls per question. For the six new conversational developer-path cases, two passed (history pronoun and corrected folder); two identity cases were unsupported and two tool-attempts violated the explicitly zero-tool benchmark contract. These are valid development-path failures, but they do not demonstrate that the deployed voice conversation route has the same defect. Preserve the negative evidence in `/data/var/swaag-benchmarks/conversation-20261103/live/`.

The NEW `swaag.benchmark conversation-acceptance` subcommand invokes the REAL `CommunicationService.orchestrator_message` as used by finalized voice and chat input, with real Coder inference. Each independent case owns a separate private session root and workspace, seeded with actual durable user/assistant messages. There are no shared production sessions, configured tools, worker rights or permitted writes. The CLI preserves durable operation IDs, captures the exact observed final message and independent answer/regex oracle, asserts zero tools/workers, and writes per-case receipts under `/data/var`. The result file and session history are **not** inside the benchmark workspace; an early test discovered the resulting false-positive workspace-mutation verdict and was fixed without weakening the unchanged-workspace assertion.

On Thor, the actual deployed configuration with only development-case session and tool boundaries overridden passed **six of six canonical conversational cases** in the preserved `canonical-benchmark-v2` run. The cases cover identity including rude speech wording, explanatory follow-up from prior actual conversation, pronoun resolution selecting the correct host, latest user correction overriding prior assistant advice, and truthful denial of a previously unexecuted backup. Five fast cases took about 0.7 to 1.3 seconds with one foreground model call. The longer voice-interface explanation took approximately 17 seconds and escalated to a deep action plus completion evaluation. That fallback is slow for a short history-grounded question and warrants a targeted latency/context audit, not an unverified success claim. These six original development cases are not a representative semantic reliability rate, multi-turn scalability study, or untouched final holdout. The October 25 real multi-source false completion remains unresolved.

Focused new benchmark tests passed **33 tests**. Existing broader deterministic regression with the compatible Thor runtime passed **1,731 with three skips**, before the final standalone conversation acceptance module was added; rerun the entire suite after integration when planning deployment. Maintain actual PYTHONPATH `/data/src/github/swaag/src` in testing: the installed site-package is older and can produce an unrelated false failure.

These are tiny, hand-selected portions of one easy read-aloud speaker and not real-phone, multilingual, spontaneous conversation or tail latency estimates. ## November 3–4 night continuation: real regression findings and non-deployed fixes

The canonical acceptance catalog now has **seventeen** independent spoken/text conversational cases, up from six. The new cases include German identity, absent private facts, correcting an unsupported prior assistant claim, a possibly sent message with no receipt, forty-two seeded earlier user/assistant history messages containing a displaced fact, late user authority over an assistant suggestion, quoted destructive instructions without tool authority, short pronoun references after genuine recent context, and a conversational codename correction that is NOT an external filesystem update. Every case uses an isolated workspace and independently verifies exact persisted chronological messages, completed durable operation ID, duplicate-idempotency receipt without a second history mutation, absence of tool/worker side effects, and unchanged workspace. A new behavioral oracle additionally rejects unnecessary blocking clarification even if the generated text contains the expected noun. A narrow, intentionally isolated case checking exact earlier test-status wording finished successfully, while a vague short contextual prompt without an explicit history qualifier remains a known unreliable case.

A preliminary fifteen-case Coder run before the completion/schema changes found twelve fully passing. Three important negative results must remain visible: one short source-status explanation called unexpected tools and cost about 322 seconds; one simple follow-up produced an invalid-output loop for about 126 seconds; and one benign quoted-deletion question was originally falsely failed because the oracle demanded a lexical `delet` rather than evidence of no actual filesystem effect. The quotation-oracle defect was corrected, but fixing a test does not prove the underlying model always resolves the reference. A test-process-only deictic prompt comparison recovered the recording-upload topic but still asked an unnecessary clarification, so it was **not deployed as a supposed fix**.

The deployed action schema used to let the model emit `criticality=blocking` together with a nonempty provisional assumption even though the independent semantic validator forbids this combination, resulting in repeated rejected action calls. The now revised **portable constrained schema** branches into a blocking question with mandatory empty assumption and a separate optional-question branch. The action semantic validator still checks optional-question assumption nonemptiness because portable schema intentionally lacks `minLength`. The revised grammar was tested with the real Coder chat-completions endpoint, emitting a valid single blocking question; schema tests also cover old contract compatibility. The exact old user-facing prompt text is unchanged apart from adding a limited completion-evaluator clarification about in-chat fact revisions.

A genuine two-process durable conversation-restart experiment failed initially because the completion evaluator misinterpreted `Correction: replace the project codename Rook with Cedar` as a demand to edit a file and repeatedly rejected its own conversational acknowledgement before an unrelated backend timeout. Its isolated operation remained `outcome_unknown` and was NOT retried. The completion-evaluator system prompt now explicitly distinguishes changes confined to facts stated in the ongoing conversation from real external operations and mandates actual observed receipts for the latter. A fresh two-process rerun then recovered the original durable receipt without modifying history, accepted the correction, and replied `Cedar` from the restored conversation without tools or workers. The reusable source module `swaag.benchmark.conversation_restart_acceptance` provides explicit `--phase first` and `--phase second` commands, using a caller-provided unique private `--output` root and `--config`; it refuses to replay already attempted uncertain second-phase operations. Only accept first/second output after distinct process runs and the second receipt has actually been verified.

The earlier full test pass under the new longer completion prompt found a context-budget-sensitive expectation in `test_reexpanded_completion_evidence_projects_only_after_overflow`: it used an artificially tiny 900-token context window and assumed the independently projected evidence should remain unprojected. With the longer correctly scoped completion system prompt, even exact excerpt references crossed that tiny limit. Reassessing the actual context budget at 1,400 tokens restored its intended exact-search and non-projection check. This is a change to the synthetic benchmark window, not relaxed source-hash or provenance checking. The initial full-suite test reported one failure and 1,737 passes with three skips; the corrected all-tests run must be evaluated separately before claiming a completely green suite.

Real ASR tests additionally covered forty official English LibriSpeech validation/development clips with all forty HTTP calls successful, aggregate WER about 5.7% / 4.1%, and an eight-clip independent German FLEURS validation subset with 160 reference words and WER 1.25%. The FLEURS dataset viewer supplies float-WAV files; direct upload into the resident PCM16-only API correctly failed, so the isolated evaluation converts and hashes the derived 16 kHz mono PCM16 bytes and keeps the original float WAV checksums. Invalid format, wrong sample rate, stereo input and truncated WAV were all rejected with HTTP 400; a genuine two-second silent recording returned zero recognized words. These are small read-aloud slices and not spontaneous speech, loud environments, tail latency, German dialects or full-duplex turn-taking acceptance.

No `turn submitted` event was observed and the post-test service health reported zero active sessions or answer jobs. The initial test parser incorrectly looked for a `draft` or `transcript` event; actual protocol emits `asr final`. Independent post-hoc validation of the logged original event stream passed. This is direct WSS-to-ASR integration evidence, not evidence that any phone played a response or that end-to-end automatic semantic turn classification works.
