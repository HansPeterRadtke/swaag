# Foreground identity and configured model routing — October 19, 2026

## Reproduced failures

The user-facing SWAAG/Coder model is expected to answer factual conversational questions without losing the application name or inventing an unspecified model identity. In an isolated real-model holdout, the ordinary question "Who are you?" previously produced a good initial SWAAG answer, but the independent `direct_conversational_reply_check` returned false because it had neither the installed application-role source nor its model-route metadata. The full completion verifier unnecessarily reexpanded historical runtime/audit material and sometimes rewrote an accurate answer into a generic response that omitted SWAAG. A separate combined question, "Who are you, and which model is answering my message?", could not converge because the snapshot exposed backend URLs without the actual configured model ID. The independent reviewer repeatedly rejected unsupported claims of absent model information, and the run exhausted its 130-second bound.

**Important benchmark correction:** Earlier isolated scripts set `tools.staged_discovery=False`, unlike installed `/etc/swaag/voice-agent.toml` where it is `true`. That caused a much larger initial 36,915-character action message and 20,285-character response-format schema in a simple identity benchmark. A correct, staged-discovery baseline reduced the first action's actual `prompt_tokens` to approximately 4,407, so the earlier 74-second identity timing must not be passed off as representative production latency. Always record staged-discovery, context settings, exact model route and raw model events when comparing latency.

## Source-grounded correction

The installed `system_foreground.txt` policy explicitly identifies the software as SWAAG's user-facing assistant and orchestrator and instructs the agent not to invent other titles or an underlying model identity. The lightweight independent `foreground_reply_check` now reads **only the first two sentences of that trusted local policy**, not action-model-selected instructions, tool schema content, prior agent claims, or model-authored metadata. It includes those as an explicitly bounded application-identity evidence component alongside the preserved authoritative user request, applicable earlier context and current model-independent system snapshot. It still cannot authorize tools, change user intent, invent effects or bypass task-state freshness checks.

`CommunicationService._orchestrator_runtime_snapshot()` now includes `model_routing.foreground` and `model_routing.default_worker` drawn directly from the configured live `AgentRuntime` instances, with separate `requested_model_id`, `configured_profile` and `base_url` for each. This distinction matters on Thor: the foreground model is the configured Qwen3-Coder, while default workers use Qwen3.8 Q8. The snapshot explicitly labels these as **configured routes, not attestation of the remote model binaries**. The direct checker receives explanatory model-route context only when an actual nonempty configured foreground ID exists. It does not turn a missing model field into a purported fact. Task-state fingerprints continue to cover mutable worker/plan/authority state; immutable model config for an instantiated service does not create false task-state changes.

The independent checker treats installed role metadata and the qualified configured model route as sufficient *source evidence for those facts only*. It must still refuse unsupported claims of Android playback, worker effects, permissions or completed external work and send unresolved substantive work to the full independent verifier. No code pattern-matches the user's question to synthesize an answer or skips model-selected tool use.

## Discovered regression: model ID versus worker model route key

The first staged-discovery *cross-role* live trial after exposing configured model names uncovered a separate, serious compatibility failure. The Coder saw the true foreground/default-worker **model IDs** in the runtime snapshot and repeatedly passed those model IDs as `plan_spec.nodes[].model_key`. That field is actually a routing **key**, not a model name: by default only `null` or the literal `default` is valid; additional names exist only when the user has configured `communication.model_routes`. The orchestration API correctly failed closed and returned `model route 'qwen38-27b-q8-full-262k' is not configured` (and once the Coder model's ID). In this isolated run the model repeated the unsupported routing request ten times and exceeded the **285-second external bound** without completing the user-authorized handoff. This is a genuine failed live acceptance caused by semantic ambiguity in trusted interface disclosures; changing model names is not itself equivalent to authorizing a route. It must never be silently converted to a successful worker launch.

The repaired snapshot now independently exposes `model_routing.available_worker_model_keys` from the **actual instantiated worker-manager mapping**, always including the default key and containing only explicitly registered named keys. Its accompanying exact contract states that `requested_model_id` is informational and *not* a `model_key`. The loaded `orchestration_control` guidance repeats this distinction at the exact point a graph is authored. Unknown keys are **still rejected** by the authoritative tool and orchestration API; no alias guessing, hidden remapping, keyword router or defaulting of invalid user requests was added. Unit tests cover default-only keys, multiple named keys, model IDs kept distinct from valid keys, source snapshot visibility and portable plan validation.

A fresh private staging-enabled Coder/Q8 test with the corrected snapshot and guidance succeeded: the foreground model performed `load_tools`, then submitted a **single valid `plan.apply` with `model_key='default'`**. The real Qwen3.8 Q8 worker executed and returned the requested `CROSS_ROLE_COMPLETE_42`; the durable plan completed. Foreground answer time was **82.5 seconds** and total elapsed including Q8 completion **118.267 seconds**, with no unsafe alias fallback. The worker had not finished when the original acknowledgement was delivered, so the queued state was truthful. The tool/plan success and the observed latency are separate conclusions: the user-facing experience is still much too slow for fluent voice interaction.

Evidence roots: failed test `/data/var/swaag-benchmarks/grounded-crossrole-staged-20261019/` and corrected passing test `/data/var/swaag-benchmarks/grounded-crossrole-keyed-20261019/`. Both used real resident model backends but disposable SWAAG state, leaving all production worker records and user conversation intact. These two single runs are not statistical assurance of semantic tool-selection reliability; further held-out multi-worker and long-conversation cases remain necessary.

## Final correction acceptance and source promotion gate

The exact updated source, including explicit worker-route selection constraints and named-route unit tests, passed the complete uncached/model-free SWAAG regression suite: **1,518 passed, 3 skipped, 0 failures in 308.97 seconds**. Raw log: `/data/tmp/swaag-grounded-identity-modelkey-final19.log`. The isolated host-configuration acceptance also confirmed from the actual installed voice TOML that `foreground.requested_model_id` matches the Coder model advertised by port 14833 and `default_worker.requested_model_id` matches Qwen3.8 Q8 on 14835, while the only selectable worker routing key in this deployment is `default`. Actual model identities and allowable tool routing keys are therefore independently distinguishable without a guessed alias.

No new SWAAG action model, state, tools, user session or systemd model service was restarted during these tests. The production package/process path remains an independent release gate; do not confuse the test worktree and disposable history with a source activated in the voice gateway.
