## Architecture / correctness findings

SWAAG is a stateful semantic-agent runtime, **not** Swagger/OpenAPI documentation tooling. Its primary human-entry contract is one persistent orchestrator (`swaag ask/chat`, or `orchestrator.message` for a real client). Worker, Task API, AG-UI, A2A and MCP endpoints serve distinct lower-level automation or integration purposes. Routing the Android/voice user into direct task submission would violate the documented architecture.

Key code partitions: `runtime.py` owns the central agent action cycle and context handling; `communication.py` owns the inbound/outbound serving boundary; `orchestration.py`, `workers.py`, `scheduler.py`, and `preemption.py` own orchestration, lifecycle and inference scheduling; `history.py`, `events.py`, `foreground_history.py` and the context/budget/token modules own persistent evidence and context admission; `model.py`, `inference.py`, `structured_output.py` and `grammar.py` own backend and constrained-call behavior; `tools/` and `environment/` implement local host tools and resource access; `mcp.py`, `external_mcp.py`, `protocol_adapters.py`, and `task_api.py` support interoperable lower-level APIs. `tests/` and `benchmark/` cover different levels of behavioral evidence. Do not conflate mocked regression success with a live end-to-end run.

Noteworthy maintenance risk: `src/swaag/runtime.py` is approximately 527 KB and `src/swaag/communication.py` approximately 294 KB. Both are exceptionally large control-plane modules; their coupling and initialization cost deserve targeted profiling and decomposed contract/branch testing, but **not** unmeasured blanket refactoring. The historical report set already records multiple regressions around foreground receipts, retries, stale state and context projection: any optimization must preserve those semantics and add regression evidence.

The existing `docs/TODO.md` is substantial, but its opening sections predate several October nineteenth integrations and include historical claims from earlier model configurations. Verify against the current running services and current source, then mark each historical statement as current, superseded or unverified. Preserve the older evidence as history rather than rewriting it to imply today's runtime passed those tests.

Measure ingress receipt, session/model queue wait, prompt build, model prefill, decoding, verification, final emission; compare model call count and preserve exact trace correlation. Goal: one successful semantic controller request for simple conversation, with zero unnecessary workers or tool calls and no contradictory identity claims.
2. **Verify the full Android voice path** from captured or injected audio through transport, STT, semantic end-of-turn, canonical user-entry routing, user-facing Coder, TTS, audio delivery and playback. 4. **Investigate excessive non-model latency** in the complete foreground call. Distinguish deterministic context/snapshot aggregation, file walks, SQLite reads, cross-process locks, schema loading, repeated network connection setup, and waits from actual LLM prefill/decoding. Profile cold and warm sessions with the same fixtures, record P50/P95 and raw step counts, and demonstrate a measurable reduction without removing required evidence. Specifically examine the large `runtime.py` and `communication.py` paths and current `foreground_world_builder.py`, `foreground_world_view.py`, `snapshot_view.py`, `orchestrator_delivery.py`, `foreground_reply_check.py`, and `session_lock.py`. New compact/fused response paths must be checked against the user's unchanged request, real worker state, and output-grounding failures before promotion.
6. **Recover every interrupted worker correctly.** Reproduce cancel, user-priority preemption, backend slot release, input revision, resumed inference and ambiguous side effects. Preserve immutable prompts, exact action receipts, event sequence and idempotency. Never replay an external write just because its model call was interrupted. **Specific code-level risk observations:**

- The direct conversational verifier, `foreground_reply_check.check_direct_reply` (14-155), makes a **second constrained model call** even after an otherwise valid tool-free first reply. It can then fall back into the full completion evaluator; the extra inference is real, not a deterministic copy. In `AgentRuntime._run_model_tool_loop` around 1550-1620, verification is still mandatory when configured. Measure and qualify semantic correctness before changing that policy; avoid claiming every question is single-call.
- A model-proposed exact-word-count field can invoke an additional full constrained generation, `_repair_exact_word_count` (2026-2138), and then completion validation. The compact first-reply path defers mismatched proposed counts, but it does not prove all unnecessary repair work is eliminated. The production prompt explicitly requires `exact_word_count=null` unless the user requests it; test that behavior against actual caller state.
- Foreground snapshot reuse still runs synchronous revision checks (`communication.py` 1775-1833), potentially querying worker cursors/controls across histories. The background builder reads latest worker events and active graph nodes. This appears considerably better than replaying every history, but the aggregate cost with many workers and long sessions must be benchmarked, not assumed negligible. Current snapshots are **per-source consistent**, not a cross-database transaction, and can go stale while model generation runs.
- The `communication.py` `_process_orchestrator_receipt` path (2349-2400) scans full durable history on certain resume/replay branches. `runtime.py` `_evaluate_completion` (2722 onward) also loads full history and can request several model-authored evidence projections. These are concrete hotspots for long sessions, although no claim about their current measured duration is warranted without tracing the exact production call.
- Source dimensions are unusual: `runtime.py` has 11,454 lines with one 848-line action loop, while `communication.py` has 6,628 lines and a single HTTP handler spanning 418 lines. Refactoring should follow measured bottlenecks and isolated tests, not file size alone.
